ARCHITECTURE OVERVIEW
---------------------
Multi-module Maven project: an annotation-driven workflow orchestrator library
(orchestrator-starter) backed by MongoDB + Kafka, with a production service
(digital-instrument-service) integrating Enigio trace:original, a signing
service (docuseal-signing-service), and a mock vendor for testing.

The library is well-architected overall: transactional outbox, jittered retry,
two-layer idempotency, gate/poll/sleep step modes, saga compensation, parallel
steps with join, signal-based communication, and child workflow support.

SECTION 1: BUGS
================================================================================

1.1 FLOWORCHESTRATOR — VERSION CONFLICT RETRY MAY SILENTLY DROP DOMAIN FIELDS
    File: orchestrator-starter/.../flow/FlowOrchestrator.java:301-314
    Severity: HIGH

    The 3-attempt optimistic lock retry loop copies only `version` and
    `currentStep` from the fresh DB read. If the reply consumer updated other
    fields between the read and save, those changes are overwritten by the
    stale in-memory flow object. After 3 failed attempts, the loop exits
    WITHOUT saving — domain fields set by the step handler may be lost.

    Recommendation: On final failure, log a warning and attempt a partial
    $set update with the domain fields from the in-memory flow object, or
    increase the retry window and copy more fields from the fresh version.

1.2 FLOWORCHESTRATOR — STEP COMPLETION SAVED BEFORE PARALLEL/ADVANCE CHECK
    File: orchestrator-starter/.../flow/FlowOrchestrator.java:286-313
    Severity: MEDIUM

    After step success, `flow.getCompletedSteps().add(stepName)` and
    `saveFlow(flow)` happen BEFORE `advanceToNextStep()`. If the app crashes
    between `saveFlow()` and the Kafka publish in `advanceToNextStep()`, the
    flow is persisted with the step marked completed but the next step is
    never published. Recovery scanner will eventually catch this, but there's
    a gap equal to `staleThresholdMinutes` (default 15 min).

1.3 FLOWORCHESTRATOR — SIGNAL RACE CONDITION ON IN_PROGRESS FLOWS
    File: orchestrator-starter/.../flow/FlowOrchestrator.java:492-515
    Severity: MEDIUM

    When a signal arrives for an IN_PROGRESS flow, it uses `mongoTemplate.updateFirst`
    with `$push` to append to `pendingSignals`. But the concurrent step execution
    (on a different thread/consumer) may be reading `pendingSignals` at the same
    time via `drainPendingSignals()`. Since MongoDB reads are not isolated from
    concurrent writes without transactions, a signal queued between the read and
    the `setPendingSignals(null)` in `drainPendingSignals` would be lost.

1.4 FLOWORCHESTRATOR — PUBLISHREPLY SWALLOW EXCEPTIONS
    File: orchestrator-starter/.../flow/FlowOrchestrator.java:380-398
    Severity: MEDIUM

    `publishReply()` catches ALL exceptions and only logs a warning. If Kafka
    is down, the reply is silently lost and the flow stalls in reply mode.
    The outbox pattern is NOT used for replies — there's no recovery mechanism.

    Recommendation: Either throw the exception to trigger Kafka retry, or write
    a reply outbox event as a safety net.

1.5 STEPREGISTRY — GETCOMPLETEDSTEPSBEFORE RETURNS MUTABLE SUBLIST
    File: orchestrator-starter/.../flow/StepRegistry.java:108-112
    Severity: LOW

    `orderedStepNames.subList()` returns a view of the underlying list. While
    `orderedStepNames` is created via `List.copyOf()` (immutable), `subList()`
    on an immutable list still returns a view. If a caller accidentally
    modifies the returned sublist, it throws UnsupportedOperationException —
    which is safe but surprising. `runCompensation` and `runCancellation`
    both iterate this list in reverse, which is fine.

1.6 ENIGIOINSTRUMENTFLOW — HARDCODED 72H EXPIRY OVERRIDES CONFIG
    File: digital-instrument-service/.../flow/EnigioInstrumentFlow.java:154,308
    Severity: LOW

    `waitUntil(() -> ..., Duration.ofHours(72))` hardcodes 72h for approval
    gates, while `approvalExpiryHours` is configurable (default 72h). These
    two values can diverge — the `waitUntil` expiry is independent of the
    manual expiry check above it. If someone changes `approvalExpiryHours`
    to 48h, the manual check fires at 48h but `waitUntil` still parks for 72h.

    Recommendation: Use `Duration.ofHours(approvalExpiryHours)` in the
    `waitUntil` call.

1.7 SECURITYCONFIG — API KEY COMPARED VIA .equals() (TIMING ATTACK)
    File: digital-instrument-service/.../config/SecurityConfig.java:73
    Severity: LOW

    `apiKey.equals(key)` is vulnerable to timing attacks. Use
    `MessageDigest.isEqual()` or `BCrypt.checkpw()` for constant-time comparison.

1.8 SEEDDATAINITIALIZER — RUNS ON EVERY NON-PROD STARTUP
    File: digital-instrument-service/.../config/SeedDataInitializer.java:31-36
    Severity: LOW

    Checks `countDocuments() > 0` to skip seeding. But if the collection has
    documents from a previous version with a different schema, the seed is
    skipped. Also, the count check is not atomic — two instances starting
    simultaneously could both see count=0 and seed duplicate data.

1.9 DOCUSEAL EMAILSERVICE — NULL CHECK MISSING
    File: docuseal-signing-service/.../client/EmailService.java
    Severity: MEDIUM

    The `enabled` flag is set based on whether `mailSender` is null, but the
    `send()` method does not check `enabled` before calling `mailSender.send()`.
    If `mailSender` is null, this will throw a NullPointerException.

SECTION 2: DESIGN GAPS & IMPROVEMENT AREAS
================================================================================

2.1 NO OBSERVABILITY / DISTRIBUTED TRACING INTEGRATION
    Severity: HIGH

    The library uses MDC for log correlation (flowId, stepName, parentFlowId)
    but does NOT integrate with OpenTelemetry or Micrometer Tracing for
    distributed traces. In a multi-service environment, you cannot trace a
    request from the REST API → Kafka → step execution → vendor call → reply.

    Recommendation: Add a `Tracer` abstraction that wraps the OpenTelemetry API,
    with a noop implementation by default. Propagate trace context in
    StepCommandMessage/StepReplyMessage headers.

2.2 NO CIRCUIT BREAKER ON VENDOR CALLS
    Severity: HIGH

    The EnigioClient calls go directly through Feign without a circuit breaker
    (Resilience4j or similar). If the Enigio API is down, every step execution
    will attempt a vendor call, fail, and route to retry topics — flooding
    Kafka with retry messages. A circuit breaker would fast-fail and park
    the flow immediately.

    Recommendation: Add `@CircuitBreaker` from Resilience4j on EnigioClient
    methods, or integrate a circuit breaker into the StepErrorHandler.

2.3 NO RATE LIMITING / BACKPRESSURE
    Severity: MEDIUM

    The Kafka consumer processes messages as fast as they arrive. If 10,000
    flows start simultaneously, all first-step messages hit the consumer at
    once, which makes 10,000 MongoDB reads and 10,000 vendor API calls.
    There's no concurrency limit or rate limiter.

    Recommendation: Set `concurrency` on the Kafka listener container to
    match available resources, and consider a semaphore on vendor API calls.

2.4 NO FLOW-LEVEL DEADLINE / TIMEOUT
    Severity: MEDIUM

    Individual steps have a configurable timeout (`step.timeoutSeconds`), but
    there's no flow-level deadline. A flow can run for days (at gate steps)
    without any overall timeout. If a flow gets stuck in an infinite retry
    loop across multiple steps, there's no circuit breaker at the flow level.

    Recommendation: Add an optional `flowDeadline` field on AbstractFlow that
    fails the flow if the total elapsed time exceeds a configurable threshold.

2.5 OUTBOX PUBLISHER — SINGLE-THREADED, NO BATCHING
    File: orchestrator-starter/.../outbox/OutboxPublisher.java:49-77
    Severity: MEDIUM

    The outbox publisher fetches up to 100 events and publishes them one at a
    time with synchronous `.get()` on each Kafka send. This creates a
    bottleneck — the step transition latency is at least `outbox.pollIntervalMs`
    plus the Kafka round-trip time per event.

    Recommendation: Use `kafkaTemplate.send()` without `.get()` (fire-and-forget
    with callbacks) for non-first-step events, or batch the sends.

2.6 NO SCHEMA VALIDATION ON KAFKA MESSAGES
    Severity: MEDIUM

    StepCommandMessage and StepReplyMessage are plain POJOs deserialized via
    Jackson. If a message with a missing or mistyped field is published (e.g.,
    `flowId` is accidentally an integer), the consumer throws a generic
    deserialization exception with no meaningful error message.

    Recommendation: Add JSON Schema validation or at minimum validate required
    fields after deserialization in the consumer.

2.7 FLOWORCHESTRATOR — GOD CLASS (1336 LINES)
    File: orchestrator-starter/.../flow/FlowOrchestrator.java
    Severity: MEDIUM

    FlowOrchestrator handles step execution, retry logic, compensation,
    cancellation, signals, child workflows, parallel join, flow search,
    serialization, timeout execution, and MDC management. This makes it
    difficult to test in isolation and violates single responsibility.

    Recommendation: Extract into focused classes:
    - StepExecutor (execute + timeout)
    - FlowAdvancer (advanceToNextStep + parallel join)
    - CompensationRunner (runCompensation + retryCompensation)
    - CancellationRunner (cancelFlow + runCancellation)
    - SignalProcessor (signal + drainPendingSignals)
    - ChildWorkflowManager (notifyParent + cancelChildren)

2.8 NO GRACEFUL SHUTDOWN HOOK
    Severity: MEDIUM

    When the application shuts down, in-flight step executions may be
    interrupted mid-way. The step timeout mechanism uses virtual threads
    with `future.cancel(true)`, but there's no JVM shutdown hook that
    marks in-progress flows as stale for recovery.

    Recommendation: Add a `@PreDestroy` that marks all IN_PROGRESS flows
    owned by this pod as stale (clear `claimedBy`, set `updatedAt` to past).

2.9 MISSING API VERSIONING
    File: digital-instrument-service/.../inbound/FlowController.java
    Severity: LOW

    REST endpoints are at `/flows/enigio-instrument` with no version prefix.
    If the API contract changes, existing clients will break.

    Recommendation: Use `/api/v1/flows/enigio-instrument` or similar.

2.10 NO HEALTH CHECK FOR VENDOR API CONNECTIVITY
    Severity: LOW

    The OrchestratorHealthIndicator checks outbox depth and stale flows, but
    does NOT check whether the Enigio vendor API is reachable. A Kubernetes
    liveness probe could report healthy while all vendor calls are failing.

2.11 WEBHOOK CONTROLLER — NO SIGNATURE VERIFICATION
    File: digital-instrument-service/.../inbound/WebhookController.java
    Severity: HIGH

    The webhook endpoint accepts any request with `traceOriginalId` and
    `eventType` fields. There's no HMAC signature verification. An attacker
    could forge FULLY_SIGNED webhooks to bypass the signing ceremony.

    Recommendation: Validate webhook signatures using a shared secret or
    asymmetric key, as is standard practice for vendor webhooks.

2.12 NO AUDIT LOG FOR APPROVAL ACTIONS
    File: digital-instrument-service/.../inbound/FlowController.java:127-169
    Severity: MEDIUM

    The approve endpoint sets `signingApproved` or `deliveryApproved` but
    does not record WHO approved it, WHEN, or from WHERE. For a financial
    instrument system, this is a compliance gap.

    Recommendation: Add an audit trail: store approver identity, timestamp,
    and source IP in the flow entity.

    File: orchestrator-starter/.../flow/FlowOrchestrator.java:1234-1248

    `entityClass`, `mongoTemplate`, `validator`, `signalRegistry`,

    Several public methods in FlowOrchestrator and FlowDefinition lack

SECTION 6: PERFORMANCE CONCERNS
================================================================================

6.1 OPTIMISTIC LOCKING RETRY — 3 ATTEMPTS MAY NOT BE ENOUGH
    File: FlowOrchestrator.java:301-314

    In high-concurrency scenarios with parallel steps and reply consumers,
    3 attempts may exhaust quickly. The retry doesn't use exponential backoff.

6.2 STEP LOG WRITES — NO BATCHING
    File: FlowOrchestrator.java:1190-1211

    Each step execution writes one StepExecutionLog document to MongoDB.
    At high throughput (1000 steps/second), this is 1000 individual writes/second.

6.3 RECOVERY SCANNER — FULL COLLECTION SCAN
    File: StaleFlowRecoveryService.java:129-134

    The stale flow recovery query scans by `(status, updatedAt)` with a limit.
    While there's a compound index on this, the query still needs to scan
    forward from the threshold. With millions of completed flows, the index
    selectivity for IN_PROGRESS is excellent, but the `claimedBy` check
    requires an additional filter.

6.4 IDEMPOTENCY COLLECTION — NO TTL INDEX EVIDENCE
    While OrchestratorProperties specifies `processedEventsDays = 30`, there's
    no visible TTL index creation in IndexInitializer for the processed_events
    collection. If the TTL index is missing, idempotency records accumulate
    indefinitely.

6.5 OUTBOX POLLING — 500ms INTERVAL IS A LATENCY FLOOR
    File: OutboxPublisher.java:48

    Every step transition must wait for the next outbox poll cycle. With 11
    steps in the Enigio flow, the minimum latency is 11 × 500ms = 5.5 seconds
    (assuming instant vendor responses). This is fine for the current use case
    but would be a bottleneck for faster workflows.

SECTION 8: POSITIVE OBSERVATIONS (STRENGTHS)
================================================================================

1. Transactional outbox pattern is correctly implemented — atomic flow save +
   outbox event write prevents lost messages.

2. Two-layer idempotency (consumer check-before + handler mark-after) is
   textbook correct and prevents duplicate processing.

3. Annotation-driven error handling (@RetryOn, @FailOn, @RecoverOn) is elegant
   and eliminates boilerplate try-catch blocks in step handlers.

4. The FlowDefinition base class provides clean DSL methods (waitUntil, pollUntil,
   sleep, checkpoint, startChildFlowAsync) that make flow code readable.

5. Startup validation (duplicate step orders, invalid @Compensate references,
   invalid @JoinOn groups) fails fast with clear error messages.

6. The stale flow recovery service with batch claiming is well-designed for
   multi-pod deployments — prevents duplicate recovery attempts.

7. Signal-based communication (Temporal-style) is a sophisticated feature
   rarely seen in Spring-based orchestrators.

8. Step execution timeout via virtual threads is modern and resource-efficient.

9. The mock-vendor service enables realistic end-to-end testing without
   external dependencies.

10. Comprehensive Swagger documentation on REST endpoints.

SECTION K: KAFKA IMPLEMENTATION ANALYSIS
================================================================================
Independent analysis of the full Kafka stack. All findings traced from source
code, verified line-by-line. No other assessment files were consulted.

ARCHITECTURE OVERVIEW
---------------------
The Kafka layer has 5 components:
  1. COMMAND TOPIC — @KafkaListener on OrchestratorCommandListener + RetryTopicConfiguration
  2. REPLY TOPIC — Programmatic ConcurrentMessageListenerContainer (no retry topics)
  3. OUTBOX — OutboxPublisher polls MongoDB, sends to Kafka in parallel batches
  4. MULTI-DC FAILOVER — DcAwareKafkaTemplate, DcAwareListenerManager, DcFailoverSupervisor
  5. OFFSET RECOVERY — MongoOffsetStore + MongoOffsetRecoveryListener for cross-cluster offsets

Message flow:
  startFlow → outbox event → OutboxPublisher → command topic → @KafkaListener
  → executeStep → markStepCompletedAtomic → publishReply → reply topic →
  programmatic listener → advanceAfterReply → advanceToNextStep → publishStepDirect → command topic

K.1 BUG: Post-Failover Producer and Consumer Read Different Topics (PREFIXED Policy)
  Files: DcAwareKafkaManager.java:63-69, DcAwareKafkaTemplate.java:29-33,
         TopicResolver.java:34-51, DcAwareListenerManager.java:57,124-128
  Severity: HIGH
  Analysis:
    When switchActiveDc() is called (line 63):
      - Line 68: this.originatingDc = previousDc (e.g., "dc-a")
      - Line 69: this.activeDc = newActiveDc (e.g., "dc-b")
    
    After failover, DcAwareKafkaTemplate.send() (line 30) calls:
      resolveActiveTopic(topic) → resolve(topic, activeDc="dc-b", originatingDc="dc-a")
    
    TopicResolver.resolve() (line 34-51):
      - targetDc="dc-b" != originatingDc="dc-a" → PREFIXED → "dc-a.topic"
      - Producer writes to "dc-a.topic" on dc-b's Kafka cluster
    
    Meanwhile, DcAwareListenerManager created standby containers at startup
    (line 57) with resolveTopic() which called:
      resolve(topic, targetDc="dc-b", activeDc="dc-a")
      → "dc-a.topic" (correct: reading dc-a's replicated data)
    
    After failover, switchDc() (line 93) starts dc-b's containers which
    subscribe to "dc-a.topic" — correct for reading OLD replicated messages.
    
    BUT: New messages produced AFTER failover go to "dc-a.topic" on dc-b.
    These are NOT replicated data — they're locally produced. The consumer
    reading "dc-a.topic" will see both old replicated messages and new
    locally produced ones. This actually WORKS for consumption.
    
    The REAL problem: when dc-a comes back and dc-b fails over to dc-a,
    the containers on dc-a were created at startup with:
      resolve(topic, targetDc="dc-a", activeDc="dc-a") → "topic" (unprefixed)
    But NOW originatingDc="dc-b" and activeDc="dc-a":
      Producer: resolve(topic, activeDc="dc-a", originatingDc="dc-b")
      → dc-a != dc-b → "dc-b.topic" — WRONG!
    
    Producer writes to "dc-b.topic" on dc-a's cluster, but dc-a's consumer
    reads from "topic" (unprefixed). Messages are NEVER consumed.
    
    ROOT CAUSE: originatingDc is set to previousDc at line 68 instead of

K.6 BUG: Outbox Publisher Batch-Save After Parallel Sends — Crash Loses State
  File: OutboxPublisher.java:56-104
  Severity: MEDIUM
  Analysis:
    The outbox publisher fires all Kafka sends in parallel (lines 64-91),
    then waits for all to complete with a 30-second timeout (line 96-97),
    then batch-saves all events in one MongoDB call (line 103).
    
    The .thenAccept() callback (lines 69-74) sets event.published=true in
    the Java object. The .exceptionally() callback (lines 76-89) sets
    failureCount. But these mutations are IN MEMORY only until saveAll()
    at line 103 persists them.
    
    CRASH SCENARIO:
    1. Events fetched from MongoDB (line 58) — all published=false
    2. Kafka sends fire in parallel — some succeed, callbacks set published=true
    3. JVM crashes before line 103 (saveAll)
    4. On restart, OutboxPublisher re-fetches these events — published=false in DB
    5. All events re-published to Kafka
    6. Consumer idempotency (eventId) deduplicates — mostly safe
    
    But: the batch timeout (30s) means events whose futures haven't completed
    have published=false. If saveAll runs after the timeout, those events are
    saved as unpublished despite Kafka having received them (future completed
    after the timeout but before saveAll). Next poll re-publishes them.
    
    This is at-least-once delivery by design, but the blast radius is the
    entire batch (batchSize=50 default), not individual events.

K.7 BUG: Consumer Idempotency Has TOCTOU Race — Check-Before, Mark-After
  File: OrchestratorKafkaConsumer.java:41-71
  Severity: MEDIUM
  Analysis:
    onStepCommand() uses a two-step idempotency pattern:
      1. Line 50: isProcessed(eventId) — READ from MongoDB
      2. Lines 64-68: execute the step
      3. Line 70: tryProcess(eventId) — WRITE to MongoDB
    
    Between step 1 and step 3, another consumer thread (or pod) processing
    the same Kafka message (re-delivery after rebalance) can also pass the
    isProcessed() check because neither has written yet. Both proceed to
    execute the step (step 2). The first tryProcess() succeeds. The second
    catches DuplicateKeyException and returns false.
    
    BUT: the step handler has ALREADY RUN on both threads.
    
    For idempotent step handlers, this is harmless. The doExecuteStepInner
    method has Layer 2 idempotency (completedSteps check at line 233). But
    if the step handler calls an external API with side effects (e.g., send
    email, charge payment), the API is called twice.
    
    WINDOW: The time between isProcessed() returning false and tryProcess()
    writing. Typically 100ms-2s (step execution time). During Kafka consumer
    group rebalancing, two pods can process the same message simultaneously.
