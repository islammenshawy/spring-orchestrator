EXECUTIVE SUMMARY
-----------------
Spring Orchestrator is a resilient multi-step workflow orchestration library built
on Spring Boot 4.0.5, MongoDB 7.0, and Kafka 3.x. It combines Saga orchestration,
transactional outbox, and Kafka non-blocking retry patterns. The project includes
a production reference service (Digital Instrument Service) integrating with the
Enigio trace:original vendor API, plus alternative framework implementations.

Overall the codebase is well-structured with clear separation between the library
(orchestrator-starter) and application services. However, several high-severity
bugs and missing safety guards were identified, particularly around concurrent
flow execution, state persistence races, and error handling gaps.

SECTION 1: CRITICAL BUGS (High Severity)
================================================================================

1.1 Parallel Step Completion Check Reads Wrong Collection
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~1236-1246
    Problem: markParallelStepCompleted() adds the parallel step name to
    `completedParallelSteps` but then checks `flow.getCompletedSteps()` (a
    different set) for the "all siblings done" condition. Parallel steps are
    only added to `completedSteps` via markStepCompleted(), which is NOT called
    for parallel steps in reply mode. This means join points will wait forever
    because the all-done check never passes.
    Fix: Change the check to query `flow.getCompletedParallelSteps()` or
    ensure parallel steps are also added to `completedSteps`.

1.2 advanceAfterReply Missing Cancelled Status Guard — [INVALID: code checks CANCELLED/CANCELLING]
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: 307-308
    Status: INVALID. Current code at line 307-308 already checks CANCELLED,
    CANCELLING, COMPLETED, and FAILED. This was a misread of the code in the
    original assessment.

1.3 claimStaleFlows Does Not Verify Status During Claim
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/recovery/StaleFlowRecoveryService.java
    Lines: ~278-283
    Problem: The claim updateMulti in republishBatch() only checks
    `claimedBy: null` but not the actual flow status (WAITING_RETRY/PARKED).
    Between the candidate query and the claim, the flow could be completed
    or failed by another pod, and the claim succeeds anyway.
    Fix: Add `.and("status").is(expectedStatus.name())` to the claim query
    (similar to the IN_PROGRESS recovery path).

SECTION 2: RACE CONDITIONS & CONCURRENCY ISSUES (Medium Severity)
================================================================================

2.1 CAS Bypass When mongoTemplate Is Null
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~951-955
    Problem: When mongoTemplate is null, `modified` is hardcoded to 1,
    completely bypassing the duplicate-send prevention check. In that path,
    a concurrent flow could have already been advanced.
    Fix: Even without mongoTemplate, should check if the flow was already
    advanced by another thread.

2.2 SignatureRejectedHandler Can Overwrite SIGNED Status — [FIXED]
    File: digital-instrument-service/src/main/java/com/dis/instrument/inbound/webhook/SignatureRejectedHandler.java
    Lines: 34-40
    Status: FIXED in current code. Now uses atomic findAndModify with
    `signingStatus.ne(SigningStatus.SIGNED.name())` guard instead of the
    previous two-step updateFirst + findOne pattern.
    Remaining note: the handler still calls notificationPublisher.notifyPhaseComplete()
    synchronously (.get() in NotificationService), which blocks the webhook
    thread but is now safe from 500 propagation due to the try-catch in
    WebhookController.

2.3 Dashboard Counter Race Condition (volatile int)
    File: examples/dashboard/src/main/java/com/enigio/orchestrator/dashboard/controller/DashboardApiController.java
    Lines: ~202-204, ~271
    Problem: sustainedLaunched++ and sustainedErrors++ are called from
    virtual threads but use `volatile int` instead of `AtomicInteger`.
    volatile guarantees visibility but NOT atomicity for read-modify-write.
    Fix: Change to AtomicInteger and use incrementAndGet().

SECTION 3: ERROR HANDLING GAPS (Medium Severity)
================================================================================

3.1 Empty Catch Block for MongoDB Offset Save Failure
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/autoconfigure/OrchestratorAutoConfiguration.java
    Lines: ~482-483
    Problem: catch (Exception e) { } -- completely empty catch block. If
    the MongoDB offset store fails to save offsets, DC failover recovery
    is silently broken with zero indication.
    Fix: At minimum, add a debug/warn log and consider incrementing a
    failure counter metric.

3.2 convertPayload Returns Wrong Type on Conversion Failure
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~554-564
    Problem: When objectMapper.convertValue() fails, the raw (wrong-typed)
    payload is returned. The reflection-based handler invocation will receive
    an object of the wrong type, causing cryptic ClassCastException deep
    in Method.invoke().
    Fix: Throw a clear exception or return null with a descriptive log.

3.3 deserializePayload Returns Null Silently
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~567-576
    Problem: If a queued signal's payload cannot be deserialized, null is
    returned and passed to the signal handler. If the handler expects
    non-null, this causes NPE.
    Fix: Log and skip the signal (don't invoke the handler with null).

3.4 Webhook Handler Exceptions Propagate to Vendor with HTTP 500
    File: digital-instrument-service/src/main/java/com/dis/instrument/inbound/WebhookController.java
    Line: ~117
    Problem: handler.handle() is called without try-catch. If processing
    fails (e.g., Kafka down), the RuntimeException returns HTTP 500 to
    Enigio, causing the vendor to retry endlessly. Webhooks should always
    return 200 on first delivery even if internal processing fails.
    Fix: Wrap in try-catch, log the error, return 200. Use a dead-letter
    queue or outbox for the failed notification.

3.5 No Global @ControllerAdvice for Standardized Error Responses
    File: digital-instrument-service (not found)
    Problem: Each controller handles errors differently -- some return
    ErrorResponse, some return plain Maps, some return
    ResponseEntity.internalServerError(). No centralized logging of
    unhandled exceptions.
    Fix: Create a @ControllerAdvice class that catches common exceptions
    and returns consistent ErrorResponse JSON.

3.6 updateFlowPartial Fallback Ignores Most Fields
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~1037-1048
    Problem: The fallback path only handles status, currentStep, and
    updatedAt. Other fields like completedParallelSteps, retryCount,
    nextRetryAt passed via the Map are silently dropped.
    Fix: Handle all possible fields or use a dynamic approach.

3.7 findFlows Returns Empty List Silently on Missing MongoTemplate
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Line: ~1387-1388
    Problem: Returns List.of() when mongoTemplate or entityClass is null.
    No log or indication that the search couldn't be performed. Callers
    think there are no results when the search wasn't executed.
    Fix: Throw IllegalStateException or log a warning.

SECTION 4: PERFORMANCE ISSUES
================================================================================

4.1 OutboxPublisher Blocks Scheduler Thread for Up to 30 Seconds
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/outbox/OutboxPublisher.java
    Lines: ~95-100
    Problem: CompletableFuture.allOf().get(30, TimeUnit.SECONDS) blocks the
    @Scheduled thread. If one send hangs (broker partition leader election),
    the entire outbox pipeline is stalled for 30s per batch.
    Fix: Use orTimeout() with a shorter timeout per-send and collect results
    asynchronously.

4.2 OrchestratorHealthIndicator Makes 2N Count Queries Per Health Check
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/autoconfigure/OrchestratorHealthIndicator.java
    Lines: ~38-52
    Problem: Makes 2N count queries (N = number of flow types) for
    IN_PROGRESS and COMPENSATION_FAILED counts. Kubernetes probes fire
    every 10-30 seconds. With 5 flow types, that's 10 MongoDB count
    queries every probe cycle.
    Fix: Cache counts briefly (e.g., 5-second TTL) or use a single
    aggregation pipeline.

4.3 findChildFlow -- O(N*M) Nested Iteration
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowDefinition.java
    Lines: ~283-291
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~630-647
    Problem: Both findChildFlow and cancelChildFlows iterate through ALL
    flow type descriptors for each child. With 10 flow types and 5 children,
    that's 50 repository lookups. Cancel repeats the same pattern.
    Fix: Cache the flow-type-to-repository mapping or add a child-flow-type
    field to the child entity.

4.4 Multiple VirtualThreadPerTaskExecutor Instances Created
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~94-95
    Problem: Each FlowOrchestrator instance creates a new virtual thread
    executor. In a multi-flow app with 5 flow types, 5 executors are created.
    Fix: Share a single executor across all FlowOrchestrator instances.

4.5 Blocking Kafka Sends in Webhook Path
    File: digital-instrument-service/src/main/java/com/dis/instrument/inbound/webhook/FlowReactivator.java
    Line: ~44
    File: digital-instrument-service/src/main/java/com/dis/instrument/service/NotificationService.java
    Line: ~80
    Problem: Synchronous kafkaTemplate.send(...).get() in the webhook
    request path means every webhook's response time is vendor_network +
    db_query + kafka_send_latency. FlowReactivator has NO outbox fallback
    unlike FlowController.reactivateFlow().
    Fix: Use async sends with callbacks. Return 200 to the vendor immediately
    and process Kafka sends asynchronously. Add outbox fallback to FlowReactivator.

4.6 All Additional Documents Decoded Into Memory at Once
    File: digital-instrument-service/src/main/java/com/dis/instrument/flow/EnigioInstrumentFlow.java
    Lines: ~362-369
    Problem: For N additional documents (each up to 10MB), all are decoded
    into byte[] in memory. With 10 documents at 10MB each, that's 100MB
    heap pressure in a single step.
    Fix: Upload documents one at a time in streaming fashion, or use
    MongoDB GridFS.

================================================================================

5.1 Hardcoded API Key in Docker Compose
    File: infra/docker-compose.yml
    Lines: ~228, ~281
    Problem: DIS_AUTH_API_KEY: soak-test-key is committed to source control.
    Also VENDOR_ENIGIO_BASE_URL uses the same key. Visible in docker inspect.
    Fix: Move to a .env file (gitignored) or Docker secrets.

5.2 MongoDB No Authentication in Docker Compose
    File: infra/docker-compose.yml
    Lines: ~4-8
    Problem: MongoDB started with no MONGO_INITDB_ROOT_USERNAME/PASSWORD.
    All connection strings use mongodb://mongodb:27017 with no credentials.
    Fix: Add root credentials via environment variables and update all
    SPRING_MONGODB_URI connection strings.

5.3 No Size Limit on Signal Payloads via REST API
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/autoconfigure/FlowEndpointAutoConfiguration.java
    Lines: ~220-243
    Problem: The signal payload from the HTTP request body is passed directly
    to orch.signal() and serialized to JSON for MongoDB storage. An attacker
    could send arbitrarily large payloads, bloating MongoDB documents and
    exhausting memory.
    Fix: Add a configurable max payload size validation.

5.4 No PII Redaction in Step Execution Log Snapshots
    File: orchestrator-starter/src/main/java/com/orchestrator/starter/flow/FlowOrchestrator.java
    Lines: ~1411-1422
    Problem: When includeFlowStateInLogs is true, the entire flow entity is
    JSON-serialized and stored in orchestrator_step_log with no mechanism
    to redact sensitive fields.
    Fix: Add a @Sensitive annotation or configurable field exclusion.

5.5 Webhook Endpoint No Rate Limiting
    File: digital-instrument-service/src/main/java/com/dis/instrument/config/SecurityConfig.java
    Line: ~41
    Problem: /webhooks/** is permitAll() with no rate limiting. An attacker
    could flood the endpoint with valid-looking traceOriginalIds, consuming
    DB resources via findOne queries.
    Fix: Add rate limiting (e.g., Bucket4j or Resilience4j RateLimiter).

5.6 No HTTPS Enforcement or HSTS Headers
    File: digital-instrument-service/src/main/java/com/dis/instrument/config/SecurityConfig.java
    Problem: No requiresChannel().anyRequest().requiresSecure(), no HSTS
    headers. The service accepts plain HTTP in production profiles.
    Fix: Add HTTPS enforcement or document that TLS termination happens
    at the ingress/load balancer.

5.7 Hardcoded API Key in DocuSeal Service Config
    File: docuseal-signing-service/src/main/resources/application.yml
    Line: ~20
    Problem: api-key has a default value that looks like a real DocuSeal
    API key, committed to source control.
    Fix: Remove the default value; make the env var required without a
    fallback. Also remove personal email addresses (lines ~27-28).

SECTION 11: CRASH RESILIENCE ANALYSIS
================================================================================
This section traces EVERY write point in the system and asks: "What if the
process crashes here?" Each scenario is verified against idempotency, outbox,
saga compensation, retry architecture, and failover recovery guarantees.

11.0 METHODOLOGY
----------------
Crash points are ordered by the system's architectural layers. For each:
  - SCENARIO: exact line range and what happens
  - VIOLATION: which guarantee(s) are at risk
  - RECOVERY: does the system self-heal?
  - SEVERITY: BROKEN (guarantee violated), DEGRADED (recovery exists but delayed
    or incomplete), OK (fully self-healing)

11.11 ROOT CAUSE ANALYSIS — WHY DO THESE GAPS EXIST?
================================================================================

1. IN-MEMORY / PERSISTENCE ATOMICITY GAP (I2, G1, G2 remain)
   WAS: The library mutated the in-memory flow object and then saved it to
   MongoDB in a separate step. Signal $push (MongoDB) happened between
   read and save → overwritten by stale in-memory state.
   FIXED for signal overwrite by swapping drain before save. The remaining
   issue is I2: markStepCompleted mutates in-memory (completedSteps.add),
   then saveFlowWithRetry later. Crash between them loses the step completion.
   Also G2: drainPendingSignals uses findAndModify (read-and-clear),
   crash during processing = signals cleared but not applied.

2. COMPENSATION IS NOT RECOVERABLE → [FIXED]
   WAS: runCompensation and runCancellation set intermediate statuses
   (COMPENSATING, CANCELLING) but neither the recovery service nor the
   stale flow scanner handled them.
   FIXED: Both handlePermanentFailure and markDeadLettered now set
   COMPENSATING before running compensation. retryCompensation accepts
   COMPENSATING. recoverStuckCompensation added to recovery scanner.
   
   REMAINING GAP: cancelFlow rejects CANCELLING status when
   recoverStuckCompensation tries to re-run cancellation. See S5 note.

3. MISSING STATUS GUARDS → [FIXED]
   WAS: doExecuteStepInner checked COMPLETED, CANCELLED, CANCELLING but
   NOT WAITING_RETRY or PARKED.
   FIXED: WAITING_RETRY with future nextRetryAt is now guarded (lines 187-195).
   PARKED status still not explicitly checked — but PARKED flows shouldn't
   normally receive step commands (they're woken by scheduler via
   nextRetryAt, which uses WAITING_RETRY semantics).

4. SIGNAL PROCESSING ORDERING → [PARTIALLY FIXED]
   WAS: drainPendingSignals ran AFTER saveFlowWithRetry, causing signal loss.
   FIXED: drainPendingSignals now runs BEFORE saveFlowWithRetry.
   REMAINING: drainPendingSignals clears all signals from MongoDB atomically
   (findAndModify) before processing. Crash during processing loses unprocessed
   signals (G2). Should process-then-clear per signal.

5. WEBHOOK ERROR PROPAGATION → [FIXED in revision 2]
   WAS: Webhook handlers threw exceptions → HTTP 500 → vendor retry storms.
   FIXED: WebhookController wraps handler.handle() in try-catch, always
   returns 200.

11.12 RECOMMENDED FIXES FOR CRASH RESILIENCE
================================================================================

1. **Make markStepCompleted + saveFlow atomic** (fixes I2):
   Move saveFlow into markStepCompleted. Use MongoDB $addToSet for
   completedSteps (idempotent) and $set for retry/reset fields in a single
   atomic update. Never rely on in-memory state across save boundaries.

2. **Swap drainPendingSignals and saveFlowWithRetry order** (fixes SIG-BUG, G2):
   Currently: saveFlowWithRetry → drainPendingSignals
   Should be: drainPendingSignals → saveFlowWithRetry
   This ensures signals are drained atomically from MongoDB BEFORE the
   in-memory flow is persisted. The drained signals are applied to the
   in-memory flow, and then the updated flow is saved.

3. **Process-then-clear for signal draining** (fixes G2):
   Instead of findAndModify (read-and-clear), read all pending signals,
   process them one at a time, and remove each from MongoDB after successful
   processing. Use $pull for individual signal removal.

4. **Add COMPENSATING/CANCELLING to recovery scanner** (fixes S1-S5):
   The StaleFlowRecoveryService should also handle flows stuck in
   COMPENSATING or CANCELLING status for longer than staleThresholdMinutes.
   Re-run runCompensation or runCancellation (handlers must be idempotent).

5. **Run compensation BEFORE marking FAILED** (fixes S1):
   In handlePermanentFailure and markDeadLettered, run runCompensation()
   FIRST, then only mark FAILED after compensation completes (or
   COMPENSATION_FAILED if compensation fails).

6. **Add WAITING_RETRY/PARKED guard to doExecuteStepInner** (fixes I3, R4):
   Similarly to CANCELLED/CANCELLING, check for WAITING_RETRY and PARKED
   and return early with a log message.

7. **Add error boundary in WebhookController** (fixes W3):
   Wrap handler.handle() in try-catch. Log the error. Always return 200.
   Use outbox/dead-letter for failed notifications.

8. **Add idempotency key to startFlow API** (fixes START1):
   Accept an optional idempotency key header in FlowController.startFlow.
   Check if a flow with that key already exists before creating a new one.

9. **Log offset save failures** (fixes OR3):
   Replace empty catch block with at least a debug log. Add a failure
   counter metric so operators can detect persistent offset store issues.

10. **Reconcile save order in doExecuteStepInner** (fixes multiple):
    The correct order should be:
    a. Execute step handler (produces results in in-memory flow)
    b. drainPendingSignals (atomically from MongoDB, apply to in-memory)
    c. markStepCompleted + saveFlowWithRetry (persist everything atomically)
    d. publishReply / advanceToNextStep (Kafka publish for next step)

    new messages go to local topics:

12-B.1 BUG: Outbox Publisher Fires-and-Forgets, Then Batch Saves — Lost Events on Crash
  File: OutboxPublisher.java:56-104
  Severity: HIGH
  Problem: The outbox publisher sends all Kafka messages in parallel (lines 64-91),
    then waits for all futures with a 30-second timeout (line 96-97), then batch-saves
    all events (line 103). The critical gap:
    
    1. kafkaTemplate.send() returns a CompletableFuture
    2. The .thenAccept() callback (lines 69-74) mutates event.setPublished(true) IN MEMORY
    3. The .exceptionally() callback (lines 76-89) mutates event.setFailureCount() IN MEMORY
    4. repository.saveAll(events) at line 103 persists ALL mutations in ONE batch
    
    If the JVM crashes between step 2/3 and step 4:
    - Event was successfully published to Kafka (consumer will process it)
    - But event.published is still FALSE in MongoDB
    - On restart, OutboxPublisher re-publishes the SAME event
    - Consumer idempotency (IdempotencyService.tryProcess) deduplicates, BUT:
      the eventId is regenerated at creation time (FlowOrchestrator line 1356:
      StepCommandMessage.builder().eventId(UUID.randomUUID().toString())).
      The SAME outbox event has the SAME eventId, so tryProcess correctly deduplicates.
    
    HOWEVER: if the batch save times out (30s limit at line 97), the remaining
    events that haven't completed their futures are still marked as unpublished.
    The code catches the timeout (line 98-99) and proceeds to saveAll — but events
    whose futures didn't complete in time have:
    - event.published = false (callback never ran)
    - event.failureCount unchanged
    - They'll be retried next poll cycle → duplicate sends
    - But eventId is the same → consumer dedup handles it
    
    SEVERE SCENARIO: If the 30s timeout fires AND saveAll fails (e.g., MongoDB
    down), the Kafka messages ARE in the broker but MongoDB doesn't know. On
    restart, ALL events are re-published. For large batches (batchSize=50 default),
    this creates a thundering herd of duplicate messages.
    
    ACTUAL BUG: The code has no individual event ack. If even ONE future in the
    batch hangs, saveAll is delayed for ALL events. Successfully published events
    are held hostage by the slow one. On crash during this window, successfully
    published events appear unpublished and get re-sent.
    
  Fix: Save each event individually in the .thenAccept() callback (or use bulk
    write with per-event completion). Alternatively, use a two-phase approach:
    mark events as "publishing" before send, then "published" after ack. This
    bounds the duplicate window to individual events, not the entire batch.

12-B.2 BUG: Outbox Publisher Skips Unpublished Events When Batch Contains Dead-Lettered Ones
  File: OutboxPublisher.java:58
  Severity: MEDIUM
  Problem: The query at line 58:
    findByPublishedFalseAndDeadLetteredFalseOrderByCreatedAtAsc
    This correctly excludes dead-lettered events. BUT there's a subtler issue:
    
    If an event is dead-lettered (failureCount >= maxPublishRetries), it stays

    The countByDeadLetteredTrue() repository method exists but is never called.
    
    Dead-lettered outbox events mean: the flow is STUCK. The step command was
    never delivered. The flow status may be IN_PROGRESS (if the original save
    succeeded but the outbox event was written before Kafka publish). The stale

12-B.3 BUG: Consumer Idempotency Has a TOCTOU Race Window
  File: OrchestratorKafkaConsumer.java:50-70
  Severity: MEDIUM
  Problem: The consumer uses a two-step idempotency check:
    1. Line 50: isProcessed(eventId) — READ from MongoDB
    2. Lines 64-70: execute step
    3. Line 70: tryProcess(eventId) — WRITE to MongoDB
    
    Between step 1 and step 3, another consumer thread (or pod) processing the
    SAME message (Kafka redelivery after rebalance) can also pass the isProcessed
    check (step 1) because neither has written yet. Both proceed to execute the
    step (step 2). The first tryProcess (step 3) succeeds. The second tryProcess
    catches DuplicateKeyException and returns false — but the step ALREADY
    EXECUTED.
    
    Mitigation: tryProcess uses MongoDB unique index on eventId (catches
    DuplicateKeyException), so the mark-after dedup prevents double-marking.
    But the step handler between lines 64-68 has ALREADY RUN on both threads.
    For idempotent step handlers, this is fine. For non-idempotent handlers
    (external API calls with side effects), this means double execution.
    
    The same race exists in onStepReply (lines 85-100).
    
    WINDOW: Between isProcessed returning false and tryProcess saving. In
    practice, this window is ~100ms-1s (step execution time). Two pods
    processing the same Kafka message during rebalance can both be in this
    window simultaneously.
    
  Fix: Use tryProcess FIRST (check-and-mark in one query via unique index),
    then execute the step if tryProcess returns true. This eliminates the
    TOCTOU window entirely. The current pattern is "check → execute → mark"
    which is vulnerable. "Mark-first → execute" is safe because:
    - tryProcess succeeds → first consumer → execute
    - tryProcess fails → duplicate → skip
    - Crash after mark but before execute → consumer re-delivers → tryProcess
      fails (already marked) → step not executed → FLOW STUCK
    - This creates a different problem: crash-after-mark loses the step.
    - Better: use optimistic concurrency with a state machine. Mark as
      "PROCESSING" first, then execute, then mark "PROCESSED". On re-delivery,
      skip PROCESSING/PROCESSED events.

12-B.6 BUG: Failover Supervisor Race — Concurrent probeAndEvaluate From Multiple Pods
  File: DcFailoverSupervisor.java:69-107
  Severity: MEDIUM
  Problem: In a multi-pod deployment, each pod runs its own DcFailoverSupervisor
    with its own probeAndEvaluate() scheduled task. When DC-A goes down:
    - ALL pods detect the failure simultaneously
    - ALL pods transition to FAILING_OVER
    - ALL pods call kafkaManager.switchActiveDc(toDc)
    - ALL pods start standby containers for DC-B
    
    This means DC-B receives N consumer groups (one per pod) all starting
    simultaneously. While Kafka handles this via rebalancing, the concurrent
    switchActiveDc calls create a race:
    
    1. Pod-1 calls switchActiveDc("dc-b") → sets activeDc="dc-b"
    2. Pod-2 calls switchActiveDc("dc-b") at the same time → also sets activeDc="dc-b"
    3. Both call listenerManager.switchDc() → both stop dc-a containers, start dc-b
    4. On dc-b, N pods × 2 consumer sets (reply + DLT) = 2N consumer groups
    5. Kafka rebalances → some pods lose partitions → duplicate processing
    
    The supervisor stores transition events in MongoDB (line 143) but doesn't
    use distributed locking. There's no leadership election or lease — every
    pod acts independently.
    
    ADDITIONAL: The consumerId at line 47-49 uses HOSTNAME or random UUID.
    In Kubernetes, HOSTNAME is the pod name (unique). But the transition event
    doesn't prevent duplicate failovers — it's audit-only.
    
  Fix: Add distributed leadership (MongoDB-based lease or Kubernetes leader
    election). Only the leader should evaluate failover. Non-leaders should
    read the active DC from a shared store (MongoDB) and follow. Or: use
    compareAndSet on the activeDc field in MongoDB to ensure only one pod
    performs the transition.

    an outbox fallback (lines 1036-1058), publishReply's outbox fallback at
    line 375-381 writes to the outboxRepository — but the reply outbox events
    are NEVER published by OutboxPublisher because OutboxPublisher only queries
    for unpublished events and sends to the configured topic.
    
    Wait — OutboxPublisher sends to event.getTopic() (line 67), and the reply
    outbox event has topic=replyTopic (line 378). So OutboxPublisher WILL
    publish it to the reply topic. The outbox fallback works.
    
    But the blocking issue remains: the consumer thread stalls until
    delivery.timeout.ms (default 2 minutes in Kafka 3.x). During this time,
    no more messages from this partition are processed. If multiple reply
    publishes stall simultaneously, the consumer exceeds max.poll.interval.ms
    and gets kicked from the group.
    
  Fix: Same as 12.5 — use .get(timeout, TimeUnit.SECONDS). The outbox fallback
    already handles the failure case.

12-B.11 BUG: DcAwareListenerManager.resolveTopic Uses Active DC Instead of Originating DC for Standby Containers
  File: DcAwareListenerManager.java:124-128
  Severity: MEDIUM
  Problem: resolveTopic() at line 125-127:
    String activeDc = kafkaManager.getActiveDc();
    return topicResolver.resolve(originalTopic, targetDc, activeDc);
    
    When creating STANDBY containers at startup, activeDc is the ACTIVE DC
    (e.g., "dc-a"). For the standby DC (targetDc="dc-b"):
      resolve("topic", targetDc="dc-b", activeDc="dc-a")
      → dc-b != dc-a → PREFIXED → "dc-a.topic"
    
    This is CORRECT for standby: dc-b should consume dc-a's replicated data
    (MM2 prefixes with source alias). The standby container reads from
    "dc-a.topic" on dc-b's Kafka cluster.
    
    BUT: After failover, when dc-b becomes active and dc-a becomes standby,
    the resolveTopic method still uses kafkaManager.getActiveDc() which is NOW
    "dc-b". So when recreating containers (if switchDc recreates rather than
    starts existing ones), the NEW standby (dc-a) would resolve:
      resolve("topic", targetDc="dc-a", activeDc="dc-b")
      → dc-a != dc-b → PREFIXED → "dc-b.topic"
    
    This is correct for reading dc-b's replicated data on dc-a's cluster.
    
    The containers are PRE-CREATED (warm standby) and not recreated on
    failover. The switchDc method (line 93-122) only starts/stops existing
    containers. So the topic names are FIXED at creation time. After failover,
    the NEW active dc-b containers still read from "dc-a.topic" (set during
    initial creation), but dc-b should NOW be reading from "topic" (its own
    local topic, since it's now the active DC producing messages).
    
    This is the SAME issue as 12.1 — after failover, containers read from
    stale topic names. The warm standby containers have hardcoded topic names
    from creation time.
    
  Fix: Same as 12.1 — either recreate containers on failover with updated
    topic names, or use IDENTITY replication policy to avoid the issue.

12-B.12 DESIGN GAP: No Kafka Consumer Lag Monitoring or Backpressure
  File: OrchestratorAutoConfiguration.java (all listener containers)
  Severity: LOW
  Problem: There is no consumer lag monitoring built into the orchestrator.
    Spring Kafka's KafkaListenerContainerFactory provides lag metrics via
    Micrometer, but the orchestrator doesn't expose a custom health indicator
    for consumer lag. The existing OrchestratorHealthIndicator only checks:
    - Outbox pending count (outboxThreshold)
    - Stale flow count (staleThresholdMinutes)
    
    It doesn't check:
    - Consumer lag (messages behind the latest offset)
    - Consumer pause status (if Kafka paused consumption due to backpressure)
    - Error rate on consumers (deserialization failures, processing errors)
    
    In production, consumer lag is the primary signal for capacity planning.
    Without it, you can't detect:
    - Slow consumers (step handlers taking too long)
    - Partition imbalance (one partition gets all the load)
    - Kafka broker degradation (increased latency → consumers fall behind)
    
  Fix: Add consumer lag to the health indicator. Spring Kafka exposes
    kafka_consumer_fetch_rate_total and kafka_consumer_lag_records via
    Micrometer. Wire these into OrchestratorHealthIndicator.

12-B.13 BUG: notifyParentOnCompletion Uses kafkaTemplate.send().get() — Same Block-without-timeout Pattern
  File: FlowOrchestrator.java:664

  Problem: notifyParentOnCompletion() at line 664:

    Same blocking issue as 12.5 and 12-B.10. If the parent command topic is
