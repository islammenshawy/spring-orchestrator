1. CRITICAL — Data Loss / Correctness Risks

1.1  advanceToNextStep Publishes Without Outbox Safety Net [DOWNGRADED]
      -------------------------------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java:603-621

      ORIGINAL: advanceToNextStep() performs atomic CAS to advance
      currentStep, then calls publishStepDirect() to send directly.
      If Kafka send fails, the flow is stuck with currentStep pointing
      to a step that was never commanded.

      ASSESSMENT: The design is safe — not a correctness gap:
        1. CAS is atomic — MongoDB state is consistent (flow at step B)
        2. .get() blocks until broker ack — only fails if Kafka is
           truly unreachable (not transient slowness)
        3. Catch block logs warning — flow doesn't crash
        4. StaleFlowRecoveryService re-publishes after 15 min — no
           data loss, no corruption, idempotency prevents duplicates
        5. JVM crash between CAS and send is identical to current
           behavior — stale recovery handles it (true for all
           distributed systems without 2PC)

      The gap is purely latency: 15 min recovery window vs 500ms
      with an outbox. Given zero recovery events in the soak test,
      this is an edge-case optimization, not a correctness issue.

      Impact:   Low — latency improvement only (15 min → 500ms).

1.2  No MongoDB Index on traceOriginalId (Webhook Lookup) [FIXED]

2. HIGH — Reliability / Operational Gaps
================================================================================

2.1  NotificationService Fire-and-Forget Kafka Send [FIXED]
      --------------------------------------------------------
      File: digital-instrument-service/.../service/NotificationService.java:80

      ORIGINAL: kafkaTemplate.send() without .get() — notification lost
      on failure, dedup flags set after send attempt.

      RESOLVED: kafkaTemplate.send(...).get() — synchronous send.
      Dedup flags set only AFTER .get() succeeds. On failure, catch
      block logs error and dedup flags are NOT set, so next retry
      cycle re-attempts.

      Impact:   FIXED — notification delivery is now confirmed.

2.2  reactivateFlow Fire-and-Forget in WebhookController / FlowController [FIXED]
      -----------------------------------------------------------------------------
      Files:
        - digital-instrument-service/.../inbound/WebhookController.java:275
        - digital-instrument-service/.../inbound/FlowController.java:266

      ORIGINAL: Both reactivateFlow() methods called kafkaTemplate.send()
      without .get(). If send fails, flow not re-activated but caller
      gets 200.

      RESOLVED: Both now use kafkaTemplate.send(...).get() for
      synchronous sends. Exceptions caught and logged.

      Impact:   FIXED — re-activation delivery is now confirmed.

2.3  writeOutboxEvent Silently Swallows Exceptions [FIXED]
      -------------------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java:765-794

      ORIGINAL: If outbox event write fails, exception caught and logged.
      startFlow() caller gets saved flow back with no outbox safety net.

      RESOLVED: writeOutboxEvent() now throws RuntimeException on failure.
      Exception propagates to startFlow() which runs inside
      runInTransaction(). If outbox write fails, entire transaction
      rolls back — flow is NOT saved.

      Impact:   FIXED — atomic save-or-fail for flow + outbox.

2.4  No Circuit Breaker on Feign Clients [FIXED]
      ---------------------------------------------
      File: digital-instrument-service/.../vendor/enigio/feign/EnigioFeignConfig.java
            digital-instrument-service/pom.xml
            digital-instrument-service/src/main/resources/application.yml

      ORIGINAL: Three Feign clients had no circuit breaker. Vendor outage
      cascaded to thread pool exhaustion (10 × 30s read timeout per flow).

      RESOLVED: Three changes:
        1. spring-cloud-starter-circuitbreaker-resilience4j added to pom.xml
        2. application.yml: spring.cloud.openfeign.circuitbreaker.enabled: true
        3. Resilience4j config: sliding window 10, 50% failure threshold,
           30s wait in open state, 3 permitted calls in half-open.
           Time limiter at 35s.

      Impact:   FIXED — vendor outage now trips circuit breaker instead
                of exhausting thread pool.

2.5  WaitingFlowScheduler Re-publishes Without Idempotency
      -------------------------------------------------------
      File: digital-instrument-service/.../service/WaitingFlowScheduler.java:88-104

      The scheduler re-publishes step commands to Kafka for waiting flows.
      These commands bypass the idempotency check in OrchestratorKafkaConsumer
      because they use a new eventId (UUID.randomUUID()). The step handler
      may already be executing (Kafka retry topic redelivery), and this
      creates a duplicate command.

      Layer 2 idempotency (isAlreadyCompleted) in FlowOrchestrator handles
      the duplicate, but it still causes unnecessary DB reads, log writes,
      and metric noise.

      Impact:   Medium — duplicate processing overhead, not data loss.
      Fix:      Use a deterministic eventId based on flowId + stepName +
                scheduler run timestamp, or check before publishing.

      ---------------------------------------------------------------

4.2  No Alerting on COMPENSATION_FAILED Flows
      ------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java:519-526

      When compensation fails, the flow is marked COMPENSATION_FAILED and
      saved. No metric is emitted, no alert is triggered. The only way to
      discover this is via the retry-compensation endpoint or manual DB query.

      Impact:   Medium — partial compensation goes unnoticed.
      Fix:      Emit a metric (orchestrator.compensation.failed) and/or
                log at ERROR level with alerting-friendly format.

4.3  VendorSyncController Returns 502 on Any Partial Failure [FIXED]
      -----------------------------------------------------------------
      File: digital-instrument-service/.../inbound/VendorSyncController.java

      ORIGINAL: CompletableFuture.allOf().join() throws if ANY future
      fails. Entire response becomes 502 even if 3 of 4 sections succeeded.

      RESOLVED: Now iterates futures individually with try-catch per
      future.join(). Failed sections return null via getOrNull().
      Response always returns 200 with whatever sections succeeded.

      Impact:   FIXED — partial data is now returned instead of discarded.

4.4  No Rate Limiting on Webhook Endpoint
      --------------------------------------
      File: digital-instrument-service/.../inbound/WebhookController.java

      Enigio could send thousands of webhooks per second (malicious or
      misconfigured). No rate limiting, no request size limits, no
      connection throttling.

      Impact:   Medium — DoS via webhook flood.
      Fix:      Add Spring Cloud Gateway rate limiter or Bucket4j.

N.1  SecurityConfig ApiKeyFilter Never Returns 401 Directly
      -------------------------------------------------------
      File: digital-instrument-service/.../config/SecurityConfig.java:62-72

      The ApiKeyFilter.doFilterInternal() always calls
      filterChain.doFilter(request, response) regardless of whether the
      API key matches. When the key is wrong, authentication is not set,
      and Spring Security's default AuthenticationEntryPoint returns 401.
      This works but is non-standard — if some other configuration bypasses
      the default entry point, unauthenticated requests could slip through.

      Impact:   Medium — relies on Spring Security defaults for rejection.
      Fix:      Filter should explicitly return 401/403 on key mismatch.

N.2  Random UUID eventId in WebhookController, FlowController,
      StaleFlowRecoveryService (same root cause as 2.5)
      -------------------------------------------------------
      Files:
        - WebhookController.java:269 — .eventId(UUID.randomUUID())
        - FlowController.java:260 — .eventId(UUID.randomUUID())
        - StaleFlowRecoveryService.java:112 — .eventId(UUID.randomUUID())

      Each re-activation or recovery creates a new random eventId, so
      the idempotency check (ProcessedEvent by eventId) won't detect
      duplicates. Layer 2 idempotency (isAlreadyCompleted) handles it,
      but unnecessary DB reads, log writes, and metric noise occur.

      Impact:   Low — duplicate processing overhead, not data loss.
      Fix:      Use deterministic eventId based on flowId + stepName +
                a stable timestamp.

N.3  NotificationService Silently Swallows Kafka Send Failures
      ----------------------------------------------------------
      File: digital-instrument-service/.../service/NotificationService.java:85-87

      On Kafka send failure, the exception is caught and logged, but
      the method returns normally. The caller (step handler) has no way
      to know the notification failed. Failed notifications are silently
      lost with no retry mechanism.

      Impact:   Low — notifications are side effects, but lost approvals
                mean flows stall until the safety-net scheduler re-triggers.
      Fix:      Consider writing notifications to an outbox-like pattern
                or at least incrementing a failure counter.

N.4  Default API Key in application.yml
      ------------------------------------
      File: digital-instrument-service/src/main/resources/application.yml

      api-key: ${DIS_AUTH_API_KEY:changeme-dev-key}

      The default value "changeme-dev-key" is a well-known weak default.
      If deployed without setting DIS_AUTH_API_KEY, the service uses
      this predictable key.

      Impact:   Medium — trivial to bypass if env var not set.
      Fix:      Remove default value; require explicit configuration.
                Fail startup if key is not set in non-dev profiles.

N.5  HealthIndicator Doesn't Cause DOWN for COMPENSATION_FAILED
      -----------------------------------------------------------
      File: orchestrator-starter/.../autoconfigure/OrchestratorHealthIndicator.java

      COMPENSATION_FAILED flows are counted in staleFlows but do not
      affect health status (only outbox issues cause DOWN). This is
      intentional per the code comment, but means COMPENSATION_FAILED
      flows can accumulate without triggering any Kubernetes-level alert.

      Impact:   Low — operational signal, not pod health. But worth
                alerting on via metrics rather than health probes.
      Fix:      Emit a dedicated metric for COMPENSATION_FAILED count
                (see 4.2) and alert on that instead.

N.6  No @Valid on AdditionalDocumentController UploadRequest
      ---------------------------------------------------------
      File: digital-instrument-service/.../inbound/AdditionalDocumentController.java:109

      @RequestBody UploadRequest request — no @Valid annotation.
      The UploadRequest record has no Jakarta Validation constraints
      (@NotBlank, @NotNull). Manual validation covers basics but is
      inconsistent with the rest of the codebase.

      Impact:   Low — manual validation works, but inconsistent pattern.
      Fix:      Add @Valid and Jakarta Validation annotations to record.
