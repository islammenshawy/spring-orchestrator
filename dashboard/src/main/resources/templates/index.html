Crash Resilience: The Dual-Write Problem
SM & SI: Direct Kafka Publish (no outbox)
1. Call Enigio API ✓ succeeds
2. Save to MongoDB ✓ succeeds
← CONTAINER CRASHES →
3. Publish to Kafka ✗ NEVER HAPPENS
Result: MongoDB says step completed, but no Kafka message to trigger next step. Flow stuck until recovery service finds it (after stale-threshold-minutes).
Saga: Transactional Outbox Pattern
1. Call Enigio API ✓ succeeds
2. @Transactional {
   Save to MongoDB ✓
   Save outbox event ✓ ← same DB, atomic
  }
← CONTAINER CRASHES →
3. OutboxPublisher polls → finds event → sends to Kafka ✓
Result: Either both writes commit or neither does. On restart, outbox publisher picks up unpublished events. No flow is ever stuck.
Caveat: The outbox pattern only provides true atomicity on a MongoDB replica set (with mongo.transactions.enabled=true). On standalone MongoDB, the outbox write is also a separate operation — same gap as SM/SI, just narrower. For production, use a replica set.
Jitter: Preventing the Thundering Herd
No Jitter (factor=0.0)
Flow A: 2000ms → 4000ms → 8000ms
Flow B: 2000ms → 4000ms → 8000ms
Flow C: 2000ms → 4000ms → 8000ms
All retries hit at the exact same time. If the vendor was overloaded, this makes it worse.
Equal Jitter (factor=0.5) ✓
Flow A: 1000+rand(0,1000)ms → 2000+rand(0,2000)ms
Flow B: 1000+rand(0,1000)ms → 2000+rand(0,2000)ms
Flow C: 1000+rand(0,1000)ms → 2000+rand(0,2000)ms
Guarantees minimum delay + random spread. Recommended for most cases.
Full Jitter (factor=1.0)
Flow A: rand(0, 2000)ms → rand(0, 4000)ms
Flow B: rand(0, 2000)ms → rand(0, 4000)ms
Flow C: rand(0, 2000)ms → rand(0, 4000)ms
Maximum spread. Risk of very short delays (near 0). Good for high contention.
Configured via kafka.retry.jitter-factor: 0.5 (or integration.retry.jitter-factor for SI). Applied to all 3 patterns identically via JitteredExponentialBackOffPolicy in the shared common module. Formula: delay = base * (1 - factor) + random(0, base * factor)
Kafka Rebalancing: Two-Layer Idempotency
Naive approach (unsafe)
1. Mark event as processed ✓
← REBALANCE / CRASH →
2. Execute step ✗ NEVER RUNS
3. Commit offset
New consumer gets partition → message redelivered → idempotency says "already processed" → step skipped forever.
Our approach (safe)
1. Check if processed (optimization only)
2. Execute step ✓ ← handler checks result fields
← REBALANCE / CRASH →
3. Mark as processed ✗ not yet written
New consumer gets partition → message redelivered → handler: "result already set, skip API call" → completes normally.
Two layers of idempotency (all 3 patterns)
Layer Where How Protects against
Layer 1: Consumer processed_events collection Check isProcessed(eventId) before step, mark after completion Duplicate Kafka messages (normal redelivery after offset not committed)
Layer 2: Handler Each step handler (e.g. CreateDocumentHandler) Check result field: if (flow.getEnigioDocumentId() != null) skip Crash between API call success and processed_events write
Layer 1 is the fast path — avoids re-entering the step entirely. Layer 2 is the safe path — even if re-entered, the vendor API is never called twice for the same step. Together they provide effectively-once processing that survives container crashes and Kafka rebalancing.

Summary: Spring Integration delivers the same Kafka-backed resilience in half the code (470 vs ~900 lines), with fewer MongoDB collections and no custom recovery service. Saga+Outbox is the only pattern with atomic DB+Kafka writes (outbox) and built-in compensation, making it the safest choice for financial/legal workflows where zero stuck flows is non-negotiable. Statemachine adds state transition validation (the framework rejects illegal events) but requires the most code due to custom MongoDB persistence — this overhead disappears with a relational DB.

Kafka Rebalancing: Multi-Container Deployment
Default RangeAssignor (stop-the-world)
Container C joins group
↓ ALL consumers STOP ↓
A: [P0,P1,P2] → [] revoke ALL
B: [P3,P4,P5] → [] revoke ALL
↓ wait ~30s ↓
Reassign: A:[P0,P1] B:[P3,P4] C:[P2,P5]
30s of ZERO processing. P0,P1,P3,P4 didn't need to move but were revoked.
CooperativeStickyAssignor (incremental) ✓
Container C joins group
↓ only move what needs to move ↓
A: [P0,P1,P2] → revoke P2 → [P0,P1] keep running!
B: [P3,P4,P5] → revoke P5 → [P3,P4] keep running!
C: gets [P2,P5]
Only P2,P5 paused briefly. P0,P1,P3,P4 never stopped.
Container Crash During Flow: Outbox as Primary Recovery
Pod A: step UPLOAD_ATTACHMENT for flow-123
  1. API call → attachmentId saved to MongoDB ✓
  2. Outbox event written (same DB) ✓
    ← POD CRASHES →
  3. Kafka offset not committed ✗
Recovery path 1 — Outbox (fast, ~500ms):
  OutboxPublisher on any pod → polls → sends to Kafka → next step runs
Recovery path 2 — Kafka redelivery (30s):
  Rebalance → Pod B gets partition → message redelivered
  Handler: attachmentId set → skip API → advance to next step
Outbox is primary (~500ms). Kafka redelivery is the redundant safety net (~30s). Either alone recovers the flow. Together: bulletproof.
Step-Level Guarantee: "If It Passed, It Never Triggers Again"
Each step handler implements isAlreadyCompleted(flow) which checks if the vendor API result is already stored in MongoDB. Even if Kafka redelivers the message 10 times, the API is called at most once.
Retryable step (e.g., vendor returns 500):
  Attempt 1: API call → 500 → throw RetryableStepException
  → Kafka retry-0 (2s) → retry-1 (4s) → retry-2 (8s) → DLT
  isAlreadyCompleted() = false on each retry (no result yet)
Succeeded step (redelivered after crash/rebalance):
  Attempt 1: API call → success → result saved to MongoDB
  ← crash/rebalance →
  Redelivery: isAlreadyCompleted() = true → skip API call entirely
  Advance to next step → no duplicate work
Non-retryable step (e.g., validation failed):
  Attempt 1: throw NonRetryableStepException
  → flow.status = FAILED immediately → no retries, no DLT
