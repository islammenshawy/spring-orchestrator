Pattern: Saga + Transactional Outbox

POST /flows → 202 Accepted + flow ID
  │
  ├── Save flow to MongoDB (status=IN_PROGRESS)
  ├── Save outbox event (same DB — atomic on replica set)
  ├── Publish to Kafka (sync, waits for broker ack)
  ├── Return to caller (~5ms)
  │
  ▼ (async — Kafka consumer, possibly different pod)
  │
  ┌─────────────┐  command   ┌──────────────┐  reply    ┌─────────────┐
  │ Orchestrator│ ─────────→│   Executor   │ ────────→│ Orchestrator│
  │ (publishes  │           │ (runs step)  │          │ (advances   │
  │  commands)  │           │              │          │  to next)   │
  └─────────────┘           └──────────────┘          └─────────────┘

  Step 1: CREATE_DOCUMENT  → vendor API → checkpoint() → reply → next command
  Step 2: UPLOAD_ATTACHMENT → vendor API → checkpoint() → reply → next command
  Step 3: REQUEST_SIGNATURE → vendor API → checkpoint() → reply → next command
  Step 4: VERIFY_SIGNATURE  → vendor API (poll) → reply → next command
  Step 5: FINALIZE_DOCUMENT → vendor API → checkpoint() → COMPLETED

  On failure → retry-0 → retry-1 → retry-2 → DLT → @Compensate → FAILED

  Ordering:   flowId = Kafka partition key → same partition → same consumer
  Topics:     {command-topic} + {command-topic}.replies (each with retry chain + DLT)
  Scaling:    executor pods scale independently, orchestrator never blocked
  Snapshot:   reply carries full flow state → no stale DB re-read → zero data loss
  @Version:   command consumer = full save with @Version (protects rebalancing)
              reply consumer = $set partial update (bypasses @Version, no conflict)
  Multi-flow: flowType in every message → routes to correct handler
  Crash-safe: any crash at any point → recovery via outbox/Kafka/recovery service

Crash Resilience: The Dual-Write Problem

SM & SI: Direct Kafka Publish (no outbox)
1. Call Enigio API ✓ succeeds
2. Save to MongoDB ✓ succeeds
← CONTAINER CRASHES →
3. Publish to Kafka ✗ NEVER HAPPENS
Result: Flow stuck until recovery service finds it.
Saga: Transactional Outbox Pattern
1. Call Enigio API ✓ succeeds
2. @Transactional { Save + Outbox event } ✓ atomic
← CONTAINER CRASHES →
3. OutboxPublisher polls → Kafka ✓
Result: No flow is ever stuck. Outbox picks up unpublished events.
Caveat: True atomicity requires MongoDB replica set with mongo.transactions.enabled=true. On standalone, the outbox write is also separate — same gap, just narrower.

Retry with Jittered Backoff

Step fails (HTTP 500)
  ├→ commands           attempt 1  FAIL
  ├→ commands-retry-0   2s+jitter  FAIL
  ├→ commands-retry-1   4s+jitter  FAIL
  ├→ commands-retry-2   8s+jitter  FAIL
  └→ commands-dlt       Dead Letter
       ├── flow.status = FAILED
       └── @Compensate in reverse

Two-Layer Idempotency

Message arrives
  Layer 1: tryProcess(eventId)
  ├── duplicate → SKIP (fast path)
  └── first time → proceed
        Layer 2: completedWhen
        ├── TRUE → skip API (safe path)
        └── FALSE → execute step
              API → set result → checkpoint
              Layer 1: mark processed AFTER
Key: marks AFTER, not before.
Crash mid-step → redeliver → Layer 2 skips.

Crash Recovery (3 paths)

Pod crashes after step succeeds:

Path 1 — Outbox (~500ms):
  Publisher on any pod → polls → Kafka

Path 2 — Kafka redeliver (~30s):
  Rebalance → new pod → Layer 2 skips

Path 3 — Recovery service (~5 min):
  Scans stale IN_PROGRESS → re-publish

Kafka Rebalancing

CooperativeStickyAssignor:
  Only moving partitions pause.
  Others keep processing.

Pod C joins:
  A: [P0,P1,P2] → revoke P2 → [P0,P1] ✓
  B: [P3,P4,P5] → revoke P5 → [P3,P4] ✓
  C: gets [P2,P5]

Two-layer idempotency handles
any redelivered messages.

Jitter: Preventing the Thundering Herd

No Jitter (factor=0.0)
Flow A: 2000ms → 4000ms → 8000ms
Flow B: 2000ms → 4000ms → 8000ms
Flow C: 2000ms → 4000ms → 8000ms
All retries at same time. Thundering herd.
Equal Jitter (factor=0.5) ✓
Flow A: 1000+rand(0,1000)ms
Flow B: 1000+rand(0,1000)ms
Flow C: 1000+rand(0,1000)ms
Minimum delay + random spread. Recommended.
Full Jitter (factor=1.0)
Flow A: rand(0,2000)ms
Flow B: rand(0,2000)ms
Flow C: rand(0,2000)ms
Maximum spread. Risk of near-0 delays.
Formula: delay = base * (1 - factor) + random(0, base * factor). Configured via orchestrator.retry.jitter-factor.

Kafka Rebalancing: Two-Layer Idempotency Safety

Naive approach (unsafe)
1. Mark event as processed ✓
← REBALANCE / CRASH →
2. Execute step ✗ NEVER RUNS
3. Commit offset
New consumer: "already processed" → step skipped forever.
Our approach (safe)
1. Check if processed (optimization)
2. Execute step ✓ (handler checks result)
← REBALANCE / CRASH →
3. Mark as processed ✗ not yet
New consumer: "result already set, skip API" → completes normally.
