Transactional Outbox

Every state change persisted atomically with its Kafka event. No message loss even if broker is down.

Webhook-Driven Signing

Primary signal from Enigio webhooks (PARTIALLY_SIGNED, FULLY_SIGNED). Poll fallback + configurable expiry (48h).

Approval Gates

Downstream notified via Kafka topic at each phase boundary. Flow pauses until POST /approve. Expiry after 72h.

Crash Recovery

Stale flow scanner + WaitingFlowScheduler re-publish stuck flows. Idempotent steps prevent duplicate API calls.

Resilience Guarantees

What happens when things go wrong.

↻
Enigio 500/502/503

RetryableStepException routes to Kafka retry topics with jittered exponential backoff (5s → 180s cap). After 8 attempts, message goes to DLT.

⏱
Enigio Timeout

WebClient responseTimeout (10s) triggers retry. The completedWhen guard prevents duplicate API calls if the first call succeeded but response was lost.

✗
Enigio 400/403

NonRetryableStepException. Flow immediately FAILED. Downstream notified via notification topic with error details.

⇄
Enigio 409 Conflict

@RecoverOn(httpStatus=409) triggers skip recovery. Step marked completed using existing resource. No duplicate creation.

⚡
Container Crash

Transactional Outbox ensures Kafka event persisted atomically. On restart, outbox publisher re-sends. Idempotent completedWhen guards prevent re-execution.

⚙
Kafka Down

Events accumulate in MongoDB outbox. When Kafka recovers, publisher drains backlog (500ms poll). No message loss.

🔄
Signer Never Signs

Configurable expiry (dis.signing.expiry-hours, default 48h). After threshold, one final GET /status poll. If still PENDING, flow FAILED with EXPIRED. Downstream notified.

🕑
Approval Never Comes

Gate steps check dis.approval.expiry-hours (default 72h). If downstream doesn't POST /approve within threshold, flow FAILED with APPROVAL_EXPIRED notification.

🌐
Multi-Container Failover

Multiple DIS instances share Kafka consumer group. If one dies, partitions rebalance in 30s. All state in MongoDB, not memory. Zero data loss.

Flow Cancellation

How to void or cancel a running instrument flow at any point.

Cancellation Rules

Cancel Endpoint

POST /flows/enigio-instrument/{id}/cancel { "reason": "Terms rejected by legal department" } // Response (200): { "flowId": "69f53a34...", "status": "CANCELLED", "message": "Flow cancelled. CANCELLED: Terms rejected..." } // Error (400) — not cancellable: { "error": "Cannot cancel — flow not in cancellable state" }

What Happens on Cancel

1. Status set to CANCELLING
2. @OnCancel handlers run in reverse for completed steps
3. Falls back to @Compensate if no @OnCancel defined
4. Enigio: POST /documents/{id}/invalidate voids the document
5. Downstream notified: FLOW_CANCELLED
6. Status set to CANCELLED

@OnCancel in Flow Definition

// In EnigioInstrumentFlow.java: @Step(order = 2, completedWhen = "traceOriginalId != null") public void registerDocument(EnigioInstrumentEntity flow) { // ... create document on Enigio ... } @OnCancel(step = "registerDocument") public void cancelDocument(EnigioInstrumentEntity flow) { // Invalidate document on Enigio — puts it in end state // No one can possess, amend, or transfer after invalidation enigioClient.invalidateDocument(flow.getTraceOriginalId()); } @OnCancel(step = "transferDocument") public void cancelTransfer(EnigioInstrumentEntity flow) { // Cancel transfer if recipient hasn't opened yet // DELETE /documents/{transferId}/transfer-by-email enigioClient.cancelTransfer(flow.getTransferId()); }

The Offset Problem

When DC-1 fails and dis-2 starts on DC-2's Kafka Cluster B:
  • Messages are replicated via MirrorMaker 2 (data exists on Cluster B)
  • Consumer offsets are NOT replicated — __consumer_offsets is per-cluster
  • Offset numbers differ between clusters (different ordering, compaction)
  • Offset 1164 on Cluster A ≠ offset 1164 on Cluster B

MongoDB Offset Store (Solution)

Instead of relying on __consumer_offsets, we store offsets in MongoDB — which IS replicated cross-DC via replica set.
// After each processed message, saved to MongoDB: { "_id": "dis-executor|dis.instrument.commands|0", "consumerGroup": "digital-instrument-service-executor", "topic": "dis.instrument.commands", "partition": 0, "offset": 1164, // Cluster A offset "eventId": "flow-abc-123", // message key "messageTimestamp": 1714500000000, // ← this is the universal coordinate "updatedAt": "2026-05-01T..." } // On DC-2 failover, MongoOffsetRecoveryListener: // 1. Reads messageTimestamp from MongoDB (1714500000000) // 2. Calls kafkaB.offsetsForTimes(1714500000000) // → Kafka B returns: "that timestamp = my offset 1170" // 3. consumer.seek(partition, 1170) // 4. Resumes from EXACT position — zero replay, zero loss
