The Pattern

The library implements the Saga Orchestrator pattern with a Transactional Outbox for reliable message delivery. Each workflow step is a separate Kafka message, executed by a single consumer with crash-resilient retry.

Your Application Library (auto-configured) ───────────── ───────────────────────── @Flow class FlowOrchestrator @Step methods ──────────▶ ├── Step Registry @Compensate ├── Outbox Writer (atomic with flow save) @RetryOn ├── Executor Consumer (executes steps) @RecoverOn ├── Orchestrator Consumer (advances flows) @FailOn ├── Retry Topic Config (jittered backoff) @Parallel ├── Idempotency Service (two-layer dedup) @JoinOn ├── Step Audit Logger ├── Stale Flow Recovery (crash safety net) └── Compensation Engine (reverse on failure) Flow Entity ──────────▶ MongoDB extends AbstractFlow ├── your_flows (domain state) ├── orchestrator_outbox ├── orchestrator_processed_events └── orchestrator_step_log Kafka Topics (auto-created) ├── {command-topic} (step commands) ├── {command-topic}-retry-0/1/2 + -dlt ├── {command-topic}.replies (step results) └── {command-topic}.replies-retry-0/1/2 + -dlt

Decoupled Executor / Orchestrator (default)

┌─────────────┐ command ┌──────────────┐ reply ┌─────────────┐ │ Orchestrator│ ─────────▶ │ Executor │ ────────▶ │ Orchestrator│ │ (publishes │ │ (executes │ │ (advances │ │ commands) │ │ the step) │ │ the flow) │ └─────────────┘ └──────────────┘ └─────────────┘ │ Calls vendor API (30s timeout max) Executor thread: blocked during API call (up to 30s) Orchestrator thread: NEVER blocked — publishes commands, processes replies Scale executors for throughput. Orchestrator stays lightweight. To disable: orchestrator.kafka.reply-topic: "" (inline mode)

Quick Start

1. Add dependency

<dependency>
    <groupId>com.enigio.orchestrator</groupId>
    <artifactId>orchestrator-starter</artifactId>
</dependency>

2. Define your flow (one class, all steps)

@Component
@Flow(topic = "orders.commands")
@RetryOn(httpStatus = {500, 502, 503, 429})
@FailOn(httpStatus = {400, 403})
public class OrderFlow extends FlowDefinition<OrderEntity> {

    @Autowired private PaymentClient paymentClient;

    @Step(order = 1, completedWhen = "paymentId != null")
    @RecoverOn(httpStatus = 409, message = "already charged", action = RecoverAction.SKIP)
    public void chargePayment(OrderEntity flow) {
        var result = paymentClient.charge(flow.getAmount());
        flow.setPaymentId(result.getId());
    }

    @Compensate(step = "chargePayment")
    public void refundPayment(OrderEntity flow) {
        paymentClient.refund(flow.getPaymentId());
    }

    @Step(order = 2, completedWhen = "trackingNumber != null")
    public void shipOrder(OrderEntity flow) {
        var result = shippingClient.ship(flow.getAddress());
        flow.setTrackingNumber(result.getTracking());
    }
}

3. Flow entity (just your domain fields)

Extend AbstractFlow — all tracking fields (id, status, retryCount, currentStep, version, etc.) are inherited. You only declare your domain fields.

@Data
@EqualsAndHashCode(callSuper = true)
@Document(collection = "order_flows")
public class OrderEntity extends AbstractFlow {
    // Only YOUR fields — nothing else
    private BigDecimal amount;
    private String paymentId, trackingNumber, address;
}

No repository interface needed — the library auto-generates one.
No @EnableMongoRepositories — the library auto-scans its packages.

4. Configure

spring:
  data.mongodb.uri: mongodb://localhost:27017/my_db
  kafka.bootstrap-servers: localhost:9092

orchestrator:
  kafka.command-topic: orders.commands

3 files (entity, repository one-liner, flow class) and 4 lines of config.

Auto-configured: REST endpoints (POST /flows, GET /flows/{id}), Kafka retry topics, outbox, idempotency, recovery, audit logging, compensation. Disable endpoints with orchestrator.endpoints.enabled: false.

Sequential (default)

Step 1 ──▶ Step 2 ──▶ Step 3 ──▶ COMPLETED Each step is one Kafka message. Next step published via outbox after current step succeeds.

Parallel + Join

    // only runs when BOTH parallel steps completed

Retry with Jittered Exponential Backoff

Step fails (HTTP 500 from vendor) │ ├──▶ orders.commands attempt 1 FAIL │ │ │ ┌────▼─────────────────────────────────────────┐ │ │ orders.commands-retry-0 2s + jitter FAIL │ │ │ orders.commands-retry-1 4s + jitter FAIL │ │ │ orders.commands-retry-2 8s + jitter FAIL │ │ └────┬─────────────────────────────────────────┘ │ │ │ ┌────▼────┐ │ │ -dlt │ Dead Letter Topic │ └────┬────┘ │ │ │ ▼ │ DLT Handler: │ ├── flow.status = FAILED │ └── @Compensate in reverse: │ ├── undo step 2 │ └── undo step 1

Jitter prevents thundering herd

jitter = 0.0

2000ms → 4000ms → 8000ms
All retries aligned.
100 flows hit vendor
at the same instant.

jitter = 0.5 (recommended)

1000-2000ms → 2000-4000ms
Minimum delay guaranteed.
Retries spread evenly.

jitter = 1.0

0-2000ms → 0-4000ms
Maximum spread.
Risk of very short delays.

Formula: delay = base * (1 - factor) + random(0, base * factor)

Two-Layer Idempotency

Layer 1: Consumer (processed_events)

Check-only with isProcessed(eventId) before execution. Mark with tryProcess(eventId) AFTER success.

Key: checked BEFORE, marked AFTER. Failed steps are NOT marked — retries work correctly.

Layer 2: Handler (completedWhen)

SpEL: "paymentId != null". If result field already set in MongoDB → skip API call.

Result: vendor API called at most once per step.

Crash at every point — what happens

@Step(order = 1, completedWhen = "paymentId != null")
public void chargePayment(OrderFlow flow) {
    //                              ← CRASH POINT A
    var result = paymentClient.charge(flow.getAmount());
    //                              ← CRASH POINT B  ⚠️ dangerous
    flow.setPaymentId(result.getId());
    checkpoint(flow);
    //                              ← CRASH POINT C
}
// Library runs after your method:
//   save flow to MongoDB           ← CRASH POINT D
//   save outbox event              ← CRASH POINT E
//   mark processed (Layer 1)       ← CRASH POINT F
CrashStateRecoverySafe?
A before APIAPI never calledLayer 1: first time → Layer 2: false → execute normally✅
B after API, before saveVendor charged, paymentId not savedLayer 2: false → API called again⚠️ see below
C after checkpointpaymentId saved by checkpointLayer 2: true → skip API → advance✅
D after flow savepaymentId saved, no outboxRecovery service re-publishes after 5 min✅
E after outboxEverything saved except processed_eventsOutbox publisher sends (~500ms), Layer 2 skips duplicate✅
F after everythingAll persistedLayer 1: duplicate → skip entirely✅

Crash Point B: The Dangerous Window

Crash B is the only scenario where the vendor API could be called twice. No library can prevent this — HTTP and DB are two different systems.

This is not a library bug. No framework — not Temporal, not Camunda — can atomically span an HTTP call and a database write.

Three strategies to handle Crash B

1. Idempotency Key (best)

Vendor deduplicates by key. Duplicate call returns same result.

var result = paymentClient.charge(
    flow.getAmount(),
    flow.getCorrelationId()
        + ":CHARGE_PAYMENT"
);
// Retry: same key → same result
// No double charge

Stripe, Adyen, Enigio, most modern APIs.

2. Pre-check (query vendor first)

Before calling, check if previous attempt succeeded.

var existing = paymentClient
    .findByRef(flow.getCorrelationId());
if (existing != null) {
    flow.setPaymentId(existing.getId());
    checkpoint(flow);
    return; // already charged
}
var result = paymentClient.charge(
    flow.getAmount(),
    flow.getCorrelationId());
flow.setPaymentId(result.getId());
checkpoint(flow);

Works if vendor has lookup by reference.

3. Reserve + Confirm

Two steps. Reserve is safe to repeat.

@Step(order=1,
  completedWhen="reservationId != null")
void reserve(Flow f) {
    f.setReservationId(
        vendor.reserve(f.getAmount()));
    checkpoint(f);
}

@Step(order=2,
  completedWhen="paymentId != null")
void confirm(Flow f) {
    f.setPaymentId(
        vendor.confirm(f.getReservationId()));
    checkpoint(f);
}

Legacy APIs with no idempotency.

checkpoint(flow) — CRITICAL for crash safety

checkpoint(flow) saves the flow to MongoDB immediately. Without it, a crash after the API call loses the result.

✓ DO THIS

var result = vendorApi.create(...);
flow.setDocumentId(result.getId());
checkpoint(flow);
// crash-safe from here

✗ DON'T DO THIS

var result = vendorApi.create(...);
flow.setDocumentId(result.getId());
// forgot checkpoint()
// crash = documentId lost
// retry = duplicate API call

The rule: Called an API? Set the result? Call checkpoint().

When you MUST call checkpoint(): after any external API call where you set a result field.
When you can skip it: if vendor supports idempotency keys, or if the step only reads/computes (no side effects).

Transactional Outbox

Without outbox (direct Kafka publish)

1. Save flow to MongoDB     ✓
← CONTAINER CRASH →
2. Publish to Kafka         ✗ LOST
→ Flow stuck forever

With outbox (this library)

1. Save flow to MongoDB     ✓
2. Save outbox event (same DB) ✓
← CONTAINER CRASH →
3. OutboxPublisher polls    → sends to Kafka
→ Flow continues (~500ms)
Enable orchestrator.mongodb.transactions-enabled=true on MongoDB replica sets for fully atomic flow + outbox writes.

This library uses the outbox pattern: traditional MongoDB CRUD for flow state, with reliable Kafka delivery as a side effect. Choose 2PC when you need strict consistency across multiple databases. Choose event sourcing when complete audit history and time-travel are core requirements, not afterthoughts.

Saga Compensation (Rollback)

Step 1: chargePayment ✓ completed Step 2: shipOrder ✓ completed Step 3: generateInvoice ✗ FAILED (non-retryable) │ ▼ Compensation runs in reverse: ├── @Compensate("shipOrder") → cancelShipment() └── @Compensate("chargePayment") → refundPayment() │ ▼ flow.status = FAILED

Compensation runs automatically on:

  • NonRetryableStepException (immediate failure)
  • Dead letter (all Kafka retries exhausted)

Steps without @Compensate are skipped with a warning log.

Container Crash Recovery

Pod A processing flow-123, step=UPLOAD_ATTACHMENT: 1. API call succeeds → attachmentId saved to MongoDB ✓ 2. Outbox event written to MongoDB ✓ ← POD A CRASHES → 3. Kafka offset not committed ✗ Recovery path 1 — Outbox (primary, ~500ms): OutboxPublisher on any surviving pod → polls → finds unpublished event → sends to Kafka → next step executes on any available pod Recovery path 2 — Kafka redelivery (30s): Kafka detects Pod A dead (session.timeout.ms) → rebalance → Pod B gets partition → message redelivered → Layer 2: attachmentId already set → skip API → advance to next step Recovery path 3 — Safety net (5 min): StaleFlowRecoveryService scans for IN_PROGRESS flows → re-publishes step command to Kafka

Async API: Start Flow and Poll

POST /flows is async — saves the flow, publishes to Kafka synchronously (waits for broker ack), returns 202 Accepted with the flow ID. Step execution happens in the background via Kafka.

POST /flows {"title": "Contract #123", "signerEmail": "john@example.com"} │ ├── Save flow to MongoDB ~2ms ├── Save outbox event (safety net) ~1ms ├── Publish to Kafka (sync) ~5ms ├── Return 202 Accepted + flow ID │ ▼ (async — consumer thread or separate worker pod) Kafka consumer → step 1 → step 2 → ... → COMPLETED

Deployment: Combined vs Split

By default, everything runs in one pod. For production, split API and worker pods. No code change — same JAR, different YAML profile.

Combined (default — dev)

Pod A (one JVM):
  ├── REST API
  ├── Kafka Consumer
  ├── Outbox Publisher
  └── Recovery Service

Split (production)

API Pods (×2):       Worker Pods (×6):
 ├── REST API         ├── Kafka Consumer
 └── Outbox Publisher └── Recovery Service

Scale independently.
# application-api.yml — HTTP only
spring.kafka.listener.auto-startup: false
orchestrator.endpoints.enabled: true

# application-worker.yml — Kafka only
spring.kafka.listener.auto-startup: true
orchestrator.endpoints.enabled: false
Same Docker image. Run with --spring.profiles.active=api or worker.

Kafka Rebalancing

Default RangeAssignor

Pod C joins:
A: [P0,P1,P2] → [] STOP ALL
B: [P3,P4,P5] → [] STOP ALL
(wait 30s)
A: [P0,P1]  B: [P3,P4]  C: [P2,P5]
= 30s of ZERO processing

CooperativeStickyAssignor (used)

Pod C joins:
A: [P0,P1,P2] → revoke P2 → [P0,P1] keeps running
B: [P3,P4,P5] → revoke P5 → [P3,P4] keeps running
C: gets [P2,P5]
= only P2,P5 paused briefly

Step Ordering Guarantee

With multiple executor and orchestrator pods, how do we ensure steps execute in order for each flow?

Kafka partition key = flowId. Every command and reply message uses the flow's ID as the Kafka message key. Kafka guarantees that all messages with the same key go to the same partition, and each partition is consumed by exactly one consumer in the group. Therefore, all steps for a given flow are always processed by the same executor and same orchestrator instance — sequentially, never concurrently.
Flow abc-123: Command: kafkaTemplate.send(commandTopic, "abc-123", payload) ^^^^^^^^^^ partition key All commands for abc-123 → same partition → same executor pod All replies for abc-123 → same partition → same orchestrator pod Step 1 command → executor runs step 1 → reply Reply → orchestrator publishes step 2 command Step 2 command → same executor → step 2 → reply ... No race condition. Next command only exists AFTER previous reply is processed. With 10 executor pods and 5 orchestrator pods: Flow abc-123 → always partition P3 → always executor Pod-B, orchestrator Pod-A Flow def-456 → always partition P7 → always executor Pod-E, orchestrator Pod-C Different flows run in parallel. Same flow runs sequentially.

Multi-Flow Per App

Multiple @Flow classes in one app, sharing topics by default. Each flow type gets its own StepRegistry, FlowOrchestrator, and GenericFlowRepository. The flowType field in every Kafka message routes to the correct handler.

How the Snapshot Pattern Works

Command Consumer (executor): 1. Execute step (calls vendor API) 2. Save flow to MongoDB (domain fields persisted, @Version incremented) 3. Serialize flow to JSON snapshot 4. Publish reply WITH snapshot to Kafka (.get() waits for broker ack) Reply Consumer (orchestrator): 5. Receive reply with snapshot 6. Deserialize flow FROM snapshot (not from MongoDB — no stale read) 7. Advance: $set currentStep + status (partial update, bypasses @Version) 8. Write outbox event for next step command Why this works: - Step 2 completes before step 3 (synchronous) - Step 4 completes before step 5 (Kafka ordering) - Step 6 uses snapshot from step 3 (guaranteed fresh) - Step 7 uses $set (no @Version conflict with step 2) - Crash at any point: Kafka redelivers, Layer 2 catches duplicates
