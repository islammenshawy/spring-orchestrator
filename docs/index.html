The Pattern

The library implements the Saga Orchestrator pattern with a Transactional Outbox for reliable message delivery. Each workflow step is a separate Kafka message, executed by a single consumer with crash-resilient retry.

Your Application Library (auto-configured) ───────────── ───────────────────────── @Flow class FlowOrchestrator @Step methods ──────────▶ ├── Step Registry @Compensate ├── Outbox Writer @RetryOn ├── Kafka Consumer @RecoverOn ├── Retry Topic Config @FailOn ├── Idempotency Service @Parallel ├── Step Audit Logger @JoinOn ├── Stale Flow Recovery └── Compensation Engine Flow Entity ──────────▶ MongoDB (flow state) implements OrchestratorFlow Kafka Topics (auto-created) ├── {topic} ├── {topic}-retry-0 ├── {topic}-retry-1 ├── {topic}-retry-2 └── {topic}-dlt

Quick Start

1. Add dependency

<dependency>
    <groupId>com.enigio.orchestrator</groupId>
    <artifactId>orchestrator-starter</artifactId>
</dependency>

2. Define your flow (one class, all steps)

@Component
@Flow(topic = "orders.commands")
@RetryOn(httpStatus = {500, 502, 503, 429})
@FailOn(httpStatus = {400, 403})
public class OrderFlow extends FlowDefinition<OrderEntity> {

    @Autowired private PaymentClient paymentClient;

    @Step(order = 1, completedWhen = "paymentId != null")
    @RecoverOn(httpStatus = 409, message = "already charged", action = RecoverAction.SKIP)
    public void chargePayment(OrderEntity flow) {
        var result = paymentClient.charge(flow.getAmount());
        flow.setPaymentId(result.getId());
    }

    @Compensate(step = "chargePayment")
    public void refundPayment(OrderEntity flow) {
        paymentClient.refund(flow.getPaymentId());
    }

    @Step(order = 2, completedWhen = "trackingNumber != null")
    public void shipOrder(OrderEntity flow) {
        var result = shippingClient.ship(flow.getAddress());
        flow.setTrackingNumber(result.getTracking());
    }
}

3. Flow entity + repository

Extend AbstractFlow — only your domain fields. All library fields are inherited.

@Data
@EqualsAndHashCode(callSuper = true)
@Document(collection = "order_flows")
public class OrderEntity extends AbstractFlow {
    // Only YOUR fields — no boilerplate
    private BigDecimal amount;
    private String paymentId, trackingNumber, address;
}

public interface OrderRepository extends OrchestratorFlowRepository<OrderEntity> {}

4. Configure

spring:
  data.mongodb.uri: mongodb://localhost:27017/my_db
  kafka.bootstrap-servers: localhost:9092

orchestrator:
  kafka.command-topic: orders.commands

3 files (entity, repository one-liner, flow class) and 4 lines of config.

Auto-configured: REST endpoints (POST /flows, GET /flows/{id}), Kafka retry topics, outbox, idempotency, recovery, audit logging, compensation. Disable endpoints with orchestrator.endpoints.enabled: false.

Flow Types

Sequential (default)

Step 1 ──▶ Step 2 ──▶ Step 3 ──▶ COMPLETED Each step is one Kafka message. Next step published via outbox after current step succeeds.

Parallel + Join

Step 1 │ ├──▶ Step 2a (@Parallel group="prep") concurrent ├──▶ Step 2b (@Parallel group="prep") Kafka messages │ └──▶ Step 3 (@JoinOn group="prep") waits for both │ ▼ COMPLETED 
@Step(order = 2, completedWhen = "attachmentId != null")
@Parallel(group = "prep")
public void uploadAttachment(MyFlow flow) { ... }

@Step(order = 2, completedWhen = "signatureId != null")
@Parallel(group = "prep")
public void requestSignature(MyFlow flow) { ... }

@Step(order = 3)
@JoinOn(group = "prep")
public void verifyBoth(MyFlow flow) {
    // only runs when BOTH parallel steps completed
}

Retry with Jittered Exponential Backoff

Step fails (HTTP 500 from vendor) │ ├──▶ orders.commands attempt 1 FAIL │ │ │ ┌────▼─────────────────────────────────────────┐ │ │ orders.commands-retry-0 2s + jitter FAIL │ │ │ orders.commands-retry-1 4s + jitter FAIL │ │ │ orders.commands-retry-2 8s + jitter FAIL │ │ └────┬─────────────────────────────────────────┘ │ │ │ ┌────▼────┐ │ │ -dlt │ Dead Letter Topic │ └────┬────┘ │ │ │ ▼ │ DLT Handler: │ ├── flow.status = FAILED │ └── @Compensate in reverse: │ ├── undo step 2 │ └── undo step 1

Jitter prevents thundering herd

jitter = 0.0

2000ms → 4000ms → 8000ms
All retries aligned.
100 flows hit vendor
at the same instant.

jitter = 0.5 (recommended)

1000-2000ms → 2000-4000ms
Minimum delay guaranteed.
Retries spread evenly.

jitter = 1.0

0-2000ms → 0-4000ms
Maximum spread.
Risk of very short delays.

Formula: delay = base * (1 - factor) + random(0, base * factor)

Two-Layer Idempotency

Layer 1: Consumer (processed_events)

Checks eventId from Kafka message. If already in orchestrator_processed_events, skip entirely.

Protects: duplicate Kafka messages from redelivery after crash/rebalance.

Key: marked AFTER step completes, not before.

Layer 2: Handler (completedWhen)

SpEL expression on @Step: completedWhen = "paymentId != null". If true, skip API call.

Protects: crash between API call success and processed_events write.

Result: vendor API called at most once per step.

Message delivered → Layer 1: isProcessed? → NO → execute step YES → skip (fast path) Step executes → API call → result saved to MongoDB ← CRASH → processed_events NOT written Redelivery → Layer 1: isProcessed? → NO → proceed → Layer 2: completedWhen? → YES (result in DB) → skip API → advance to next step → mark processed → done

The Unavoidable Gap: API Call + Crash

No library can make an HTTP call and a database write atomic. They are two different systems. There is always a window where the API call succeeded but the result hasn't been saved yet.

var result = vendorApi.charge(amount); // money charged on vendor side ← CONTAINER CRASHES HERE → flow.setPaymentId(result.getId()); // never runs checkpoint(flow); // never runs Redelivery → completedWhen("paymentId != null") → false → vendorApi.charge() called AGAIN → double charge
This is not a library bug. It's a fundamental distributed systems constraint. No framework — not Temporal, not Camunda, not this library — can atomically span an HTTP call and a database write.

Three strategies (pick based on your vendor)

1. Idempotency Key (best)

Send a unique key with the API call. Vendor returns same result on duplicate.

var result = vendorApi.charge(
    amount,
    idempotencyKey:
      flow.getCorrelationId()
      + ":CHARGE_PAYMENT"
);
// Safe: duplicate call returns
// same result, no double charge

Stripe, Adyen, most modern APIs support this.

2. Pre-check (query before retry)

Before calling the API, check if a previous attempt already succeeded.

var existing = vendorApi
  .findByRef(flow.getCorrelationId());
if (existing != null) {
    flow.setPaymentId(existing.getId());
    return; // already done
}
var result = vendorApi.charge(amount,
    ref: flow.getCorrelationId());
flow.setPaymentId(result.getId());

Works if vendor supports lookup by reference.

3. Reserve + Confirm (two-phase)

Split into two steps. Reserve is repeatable, confirm uses the reservation ID.

// Step 1: reserve (safe to repeat)
@Step(order=1,
  completedWhen="reservationId != null")
void reserve(Flow f) {
    f.setReservationId(
        vendor.reserve(f.getAmount()));
}
// Step 2: confirm by reservation ID
@Step(order=2,
  completedWhen="paymentId != null")
void confirm(Flow f) {
    f.setPaymentId(
        vendor.confirm(f.getReservationId()));
}

For legacy APIs with no idempotency support.

checkpoint() — narrows the gap

checkpoint(flow) saves the flow to MongoDB immediately after setting the result. It can't close the gap between the API call and the set, but it closes the gap between the set and the library's own save.

@Step(order = 1, completedWhen = "paymentId != null")
public void chargePayment(OrderFlow flow) {
    var result = paymentClient.charge(flow.getAmount(),
        idempotencyKey: flow.getCorrelationId() + ":CHARGE");  // strategy 1

    flow.setPaymentId(result.getId());
    checkpoint(flow);   // persisted NOW — crash after this is safe

    auditRepo.save(new AuditRecord(flow));  // additional DB writes
}
Rule of thumb: If your vendor supports idempotency keys, use them — checkpoint() is just extra safety. If your vendor doesn't, use strategy 2 or 3, and always call checkpoint() after setting result fields.

Transactional Outbox

Without outbox (direct Kafka publish)

1. Save flow to MongoDB     ✓
← CONTAINER CRASH →
2. Publish to Kafka         ✗ LOST
→ Flow stuck forever

With outbox (this library)

1. Save flow to MongoDB     ✓
2. Save outbox event (same DB) ✓
← CONTAINER CRASH →
3. OutboxPublisher polls    → sends to Kafka
→ Flow continues (~500ms)
Enable orchestrator.mongodb.transactions-enabled=true on MongoDB replica sets for fully atomic flow + outbox writes.

Saga Compensation (Rollback)

Step 1: chargePayment ✓ completed Step 2: shipOrder ✓ completed Step 3: generateInvoice ✗ FAILED (non-retryable) │ ▼ Compensation runs in reverse: ├── @Compensate("shipOrder") → cancelShipment() └── @Compensate("chargePayment") → refundPayment() │ ▼ flow.status = FAILED

Compensation runs automatically on:

  • NonRetryableStepException (immediate failure)
  • Dead letter (all Kafka retries exhausted)

Steps without @Compensate are skipped with a warning log.

Container Crash Recovery

Pod A processing flow-123, step=UPLOAD_ATTACHMENT: 1. API call succeeds → attachmentId saved to MongoDB ✓ 2. Outbox event written to MongoDB ✓ ← POD A CRASHES → 3. Kafka offset not committed ✗ Recovery path 1 — Outbox (primary, ~500ms): OutboxPublisher on any surviving pod → polls → finds unpublished event → sends to Kafka → next step executes on any available pod Recovery path 2 — Kafka redelivery (30s): Kafka detects Pod A dead (session.timeout.ms) → rebalance → Pod B gets partition → message redelivered → Layer 2: attachmentId already set → skip API → advance to next step Recovery path 3 — Safety net (5 min): StaleFlowRecoveryService scans for IN_PROGRESS flows → re-publishes step command to Kafka

Kafka Rebalancing

Default RangeAssignor

Pod C joins:
A: [P0,P1,P2] → [] STOP ALL
B: [P3,P4,P5] → [] STOP ALL
(wait 30s)
A: [P0,P1]  B: [P3,P4]  C: [P2,P5]
= 30s of ZERO processing

CooperativeStickyAssignor (used)

Pod C joins:
A: [P0,P1,P2] → revoke P2 → [P0,P1] keeps running
B: [P3,P4,P5] → revoke P5 → [P3,P4] keeps running
C: gets [P2,P5]
= only P2,P5 paused briefly

All rebalancing config is standard Spring Boot YAML — no custom library code:

spring.kafka.consumer.properties:
  partition.assignment.strategy: CooperativeStickyAssignor
  session.timeout.ms: 30000
  heartbeat.interval.ms: 10000
  # group.instance.id: ${HOSTNAME}   # for Kubernetes StatefulSet
  # client.rack: ${KAFKA_RACK}       # for multi-region

Startup Validation

The library validates at application startup. If any rule fails, the Spring context fails to start with a clear error message:

RuleError if violated
@Compensate(step="X") must reference an existing @Step methodLists available step method names
@JoinOn(group="X") must reference an existing @Parallel groupLists available parallel groups
@Parallel steps must have completedWhenNeeded for join verification
No duplicate step orders within a @FlowLists the conflicting order number
No duplicate step names within a @FlowLists the conflicting name
@Step and @Compensate methods must accept one OrchestratorFlow parameterLists the invalid method signature
Any @SpringBootTest will catch these errors. No misconfiguration can reach production.
