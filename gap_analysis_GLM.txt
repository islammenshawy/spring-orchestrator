This document identifies design gaps, risks, and improvement opportunities
in the Spring Orchestrator library and its production consumer
(digital-instrument-service). Code is not modified — gaps are documented
for team review and prioritization.

NOTE: After an independent validation pass, several original claims were
revised. Items marked [REVISED] reflect corrections where the original
analysis was overstated or unfair. Items marked [FIXED] were resolved in
code after the initial analysis. See APPENDIX A for a change log.

================================================================================
1. ARCHITECTURE & DESIGN GAPS
================================================================================

1.1  Outbox Publisher Ordering Is Per-Instance, Not Per-Flow
     --------------------------------------------------------
     File: orchestrator-starter/.../outbox/OutboxPublisher.java

     OutboxPublisher.pollPendingEvents() fetches the 100 oldest unpublished
     events globally and publishes them in order. In a multi-instance
     deployment, each instance polls independently — there is NO cross-
     instance ordering guarantee. If Instance A writes outbox event for
     Flow-X step 2 while Instance B writes outbox event for Flow-Y step 1,
     both publish concurrently.

     Impact:   Low for single-flow correctness (idempotency handles it).
               Higher for systems that require strict global ordering.
     Fix:      Partition outbox polling by flowId hash, or use a distributed
               lock per flowId during outbox publishing.

1.2  Outbox Publisher Breaks on First Failure (Ordered Batch) [FIXED]
      ------------------------------------------------------------------
      File: orchestrator-starter/.../outbox/OutboxPublisher.java

      ORIGINAL: When publishing a batch of 100 events, the loop broke on
      the first send failure, blocking ALL 100 events permanently.

      RESOLVED: OutboxPublisher now tracks failureCount per event and
      has a configurable maxPublishRetries (default 5). Events that
      exceed the retry limit are marked deadLettered=true and skipped
      on subsequent polls. The pipeline no longer freezes on poison
      events. OutboxEvent has new deadLettered and failureCount fields.
      The repository query filters: findTop100ByPublishedFalseAndDeadLetteredFalse.

      Impact:   FIXED — poison events no longer freeze the pipeline.
      Residual: Dead-lettered events accumulate silently. No alerting
                or dead-letter collection exists (see NEW 11.1 below).

1.3  Stale Flow Recovery Only Recovers the First Flow Type [FIXED]
      ---------------------------------------------------------------
      File: orchestrator-starter/.../autoconfigure/OrchestratorAutoConfiguration.java
            (orchestratorRecoveryService bean)

      ORIGINAL: The StaleFlowRecoveryService was created with:
          first = registry.getAll().iterator().next()
      It only used the FIRST flow type's repository and command topic.

      RESOLVED: StaleFlowRecoveryService now takes FlowTypeRegistry and
      iterates ALL registered flow types in recoverStaleFlows(). Each
      flow type is recovered with its own repository and command topic.
      The flowType is now included in the recovery command message.

      Impact:   FIXED — multi-flow recovery now works correctly.

1.4  Stale Flow Recovery Re-publishes Without Updating Retry Count
     ----------------------------------------------------------------
     File: orchestrator-starter/.../recovery/StaleFlowRecoveryService.java:66-74

     When recovering a stale flow, the service re-publishes the step
     command and updates updatedAt, but does NOT reset the retryCount
     or increment a recovery counter. If the flow is stale because it
     exhausted retries and was missed by the DLT handler, re-publishing
     will hit the same failure and loop indefinitely.

     Impact:   Medium — can cause recovery loops for permanently-failing
               steps.
     Fix:      Add a recoveryCount field to AbstractFlow and a max-
               recovery-attempts config. Reset retryCount on recovery.

1.5  No Back-Pressure on Outbox Publisher [REMOVED]
      -----------------------------------------------
      Original claim: Outbox collection grows unbounded under load.
      Removed because: Outbox batch is capped at 100 per poll. Soak
      test with 280 sustained flows showed 0 unpublished events.
      Only relevant if Kafka is down for extended periods — at which
      point back-pressure on flow starts won't help (flows are already
      saved). Not a real gap at observed scale.

1.6  Reply Path Snapshot May Be Stale for Parallel Step Tracking [REVISED]
     -----------------------------------------------------------------------
     File: orchestrator-starter/.../flow/FlowOrchestrator.java

     When replyEnabled=true, advanceAfterReply() deserializes a flow
     snapshot from the Kafka message. The advanceToNextStep() method
     uses an atomic CAS (compare-and-swap via mongoTemplate.updateFirst
     with currentStep criteria) that prevents double-advancement. This
     is a solid guard — the main race condition IS mitigated.

     Residual risk: the deserialized snapshot's completedParallelSteps
     set may be stale if a concurrent webhook handler modified the flow
     between step execution and reply consumption. This only affects
     parallel step tracking, not sequential advancement.

     Impact:   Low — CAS prevents the main race; narrow residual risk
               on parallel step tracking only.
     Fix:      Low priority. Could re-read parallel step state from
               MongoDB in advanceAfterReply() instead of trusting the
               snapshot, but the CAS already prevents corruption.

2. DATA CONSISTENCY & RELIABILITY GAPS
================================================================================

2.1  Dual Concurrency Strategy Needs Better Documentation [REVISED]
      ----------------------------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java (saveFlow)

      AbstractFlow has @Version for optimistic locking. The code uses
      two concurrency strategies:
        - saveFlow() uses @Version — catches conflicts in the slow path
        - updateFlowPartial() uses atomic $set with CAS criteria — avoids
          @Version conflicts in the hot path (reply consumer, advancement)

      The original analysis called @Version "decorative." This is unfair.
      The dual strategy is intentional and documented in code comments:
      saveFlow javadoc states "Concurrency is handled by Kafka partition
      key... and two-layer idempotency, not by optimistic locking."
      updateFlowPartial javadoc states "Bypasses @Version check, preserves
      domain fields. Used by the reply consumer to avoid conflicts."

      The actual gap is not a bug but a documentation gap: this dual
      strategy is only explained in code comments, not in the README or
      architecture docs. New contributors may find the dual approach
      confusing.

      Impact:   Low — not a bug, but onboarding friction.
      Fix:      Document the concurrency model in orchestrator-starter/
                README.md: "Why two write paths and when each is used."

2.2  Transactional Outbox Is Not Atomic on Standalone MongoDB
     -----------------------------------------------------------
     File: orchestrator-starter/.../flow/FlowOrchestrator.java (startFlow)

     startFlow() uses runInTransaction() which falls back to no
     transaction if TransactionTemplate is null (standalone MongoDB).
     In that case, flowRepository.save() and outboxRepository.save()
     are separate operations — a crash between them leaves a flow with
     no outbox event (stuck forever until stale recovery).

     Impact:   Medium for single-node MongoDB deployments.
     Fix:      Document that MongoDB replica set is required for
               production, or add a compensating query in stale
               recovery that re-creates missing outbox events.

2.3  Index Creation Failures Are Silently Swallowed [REVISED]
      ---------------------------------------------------------
      File: orchestrator-starter/.../autoconfigure/IndexInitializer.java

      The TTL indexes for orchestrator_outbox, orchestrator_processed_events,
      and orchestrator_step_log ARE correctly created by IndexInitializer.
      The configuration (processedEventsDays=30, outboxDays=7, stepLogDays=90)
      is properly wired and the indexes are created at startup.

      The actual gap: IndexInitializer catches ALL exceptions with just
      a warn log, even on the initial creation. If index creation fails
      (e.g., conflicting index definition, permissions issue), the
      application starts normally and collections grow unbounded with
      no TTL cleanup — silently.

      Impact:   Low — indexes are created, but silent failure means the
                safety net has no safety net.
      Fix:      Distinguish between "index already exists" (safe to skip)
                and "creation failed" (should be fatal or at least ERROR
                level). Verify TTL indexes exist as a startup health check.

2.4  GenericFlowRepository Throws UnsupportedOperationException
     -----------------------------------------------------------
     File: orchestrator-starter/.../domain/GenericFlowRepository.java

     Many repository methods throw UnsupportedOperationException. If any
     future code path (e.g., Spring Data REST, actuator, or dashboard)
     calls findAll(Pageable) or saveAll(), it crashes. This is a ticking
     time bomb for library consumers.

     Impact:   Low today, high if any feature calls these methods.
     Fix:      Implement the commonly-needed methods (findAll with
               Pageable, saveAll) or document which methods are
               unsupported and why.

3. SECURITY GAPS
================================================================================

3.1  Auto-Generated Endpoints Have No Security Integration [REVISED]
      ----------------------------------------------------------------
      File: orchestrator-starter/.../autoconfigure/FlowEndpointAutoConfiguration.java

      POST /flows, GET /flows/{type}/{id}, POST /flows/{type}/{id}/cancel
      are exposed without security configuration. However, this is standard
      for Spring Boot starters — actuator, data-rest, and integration
      starters all delegate authentication to the consuming application.

      The library provides:
        - orchestrator.endpoints.enabled=false to disable entirely
        - orchestrator.endpoints.base-path for custom path prefix
        - @ConditionalOnWebApplication guard (no endpoints in non-web)

      The gap is a documentation item: the README should clearly state
      that consumers are responsible for securing these endpoints
      (Spring Security, OAuth2, network policy, etc.).

      Impact:   Low — standard starter behavior. Documentation fix.
      Fix:      Add a "Security" section to orchestrator-starter/README.md
                with example Spring Security configuration.

3.2  No Input Validation on Auto-Generated REST Endpoints
     -------------------------------------------------------
     File: orchestrator-starter/.../autoconfigure/FlowEndpointAutoConfiguration.java

     The POST /flows endpoint accepts Map<String, Object> and
     deserializes it into the flow entity with ObjectMapper.readValue().
     There is no validation — invalid data, extra fields, or malicious
     payloads are silently accepted. Jakarta Validation annotations on
     the entity (e.g., @NotBlank) are NOT triggered.

     Impact:   Medium — invalid flows can be created.
     Fix:      Add Validator injection and validate the deserialized
               entity before saving.

3.3  Step Execution Log May Contain Sensitive Data
     -------------------------------------------------
     File: orchestrator-starter/.../flow/FlowOrchestrator.java

     When includeFlowStateInLogs=true, the full flow state (including
     PII like signer emails, phone numbers, recipient details) is
     serialized into the step_log collection. While DIS configures a
     PiiMaskingConverter, this only applies to the main flow collection,
     not the step_log collection.

     Impact:   Medium — PII leakage in audit logs.
     Fix:      Either extend PII masking to step logs, or document
               the risk clearly and default includeFlowState to false
               (already done, but the option exists).

4. OPERATIONAL & OBSERVABILITY GAPS
================================================================================

4.1  No Metrics Export (Micrometer)
     --------------------------------
     The library has no Micrometer integration. There are no counters,
     gauges, or timers for:
       - Steps executed / failed / retried
       - Flow duration (end-to-end and per-step)
       - Outbox depth (unpublished events)
       - Stale flow recovery attempts
       - Idempotency cache hit/miss ratio
       - Kafka consumer lag

     Impact:   High — no way to monitor library health in production
               without custom code.
     Fix:      Add Micrometer counters/timers to FlowOrchestrator,
               OutboxPublisher, StaleFlowRecoveryService, and
               IdempotencyService.

4.2  No Structured Logging Correlation ID
     ---------------------------------------
     While the library logs flowId in most messages, it does NOT use
     MDC (Mapped Diagnostic Context) or structured logging with a
     consistent correlationId field. In a high-throughput system,
     correlating logs for a single flow across multiple instances
     requires manual log searching.

     Impact:   Medium — operational debugging is harder than necessary.
     Fix:      Set MDC.put("flowId", flowId) and MDC.put("stepName",
               stepName) around step execution. Clear MDC in finally.

4.3  Outbox Publisher Has No Dead-Letter Mechanism [FIXED]
      -----------------------------------------------------
      File: orchestrator-starter/.../outbox/OutboxPublisher.java

      ORIGINAL: No max-retry limit or dead-letter path. Permanently-failing
      events stayed in the outbox indefinitely, blocking all subsequent
      events.

      RESOLVED: Same fix as 1.2. Events exceeding maxPublishRetries (5)
      are marked deadLettered=true and skipped. Pipeline continues.

      Impact:   FIXED — see 1.2 for details.

4.4  No Health Indicator for Library Components
     ---------------------------------------------
     The library provides no Spring Boot HealthIndicator for:
       - Outbox depth (growing = unhealthy)
       - Stale flow count (many = unhealthy)
       - Kafka connectivity (already covered by Spring Kafka)
       - MongoDB connectivity (already covered by Spring Data)

     Impact:   Medium — Kubernetes liveness/readiness probes cannot
               detect library-specific degradation.
     Fix:      Add an OrchestratorHealthIndicator that checks outbox
               depth and stale flow count against configurable
               thresholds.

5. TESTING GAPS
================================================================================

5.1  Mock-Vendor Has Zero Tests
     -----------------------------
     File: mock-vendor/src/test/java/ (empty)

     The mock vendor has 21 source files and no tests. Given it
     simulates a real vendor API, any regression in mock behavior
     can cause false positives/negatives in DIS integration tests.

     Impact:   Medium — mock behavior is unverified.
     Fix:      Add unit tests for MockDocumentService and controller
     edge cases.

5.2  Digital-Instrument-Service Has Narrow Test Coverage [REVISED]
      ---------------------------------------------------------------
      File: digital-instrument-service/src/test/java/

      DIS has 4 test files for 59 source files. However, file count is
      a misleading metric here:
        - InstrumentFlowIntegrationTest exercises the full 11-step flow
          end-to-end (16+ test methods): gates, webhooks, cancellation,
          concurrency, and idempotency.
        - GapFixIntegrationTest adds 6 more integration test methods.
        - The integration tests cover the critical happy path and edge
          cases for the orchestration flow itself.

      The actual gap is unit tests for individual components:
        - EnigioClient Feign error handling (timeouts, 5xx retries)
        - NotificationService dedup logic
        - Individual controller edge cases (approval on wrong step,
          cancel after completion)
        - EnigioInstrumentEntity validation constraints

      Impact:   MEDIUM — integration coverage is solid; unit coverage
                for isolated component failures is thin.
      Fix:      Add targeted unit tests for EnigioClient error paths,
                NotificationService, and controller edge cases. The
                integration tests already cover the flow orchestration
                well.

5.3  No Integration Test for Multi-Flow Scenario
     -----------------------------------------------
     The orchestrator-starter has a MultiFlowTest but it's unclear if
     it tests concurrent multi-flow execution, topic routing, or
     cross-flow interference. There is no test for the multi-flow
     StaleFlowRecoveryService gap (section 1.3).

     Impact:   Medium — multi-flow is a key feature with untested
               edge cases.
     Fix:      Add integration tests for: (a) two flows with different
               entities on different topics, (b) recovery of both flow
               types, (c) flow type routing in the Kafka consumer.

5.4  No CI Chaos / Failure Injection Tests
      -----------------------------------------
      There are no Testcontainers-based chaos tests in CI for:
        - MongoDB outage during step execution
        - Kafka outage during outbox publishing
        - Concurrent webhook + Kafka consumer modifying the same flow

      However, live failover testing has been performed (killing kafka-1
      mid-soak with 280 flows — zero data loss). The soak test IS the
      chaos test in practice. Testcontainers chaos would add CI repeatability
      but the resilience has been proven against real broker failure.

      Impact:   Low — proven resilience via live failover testing.
                CI-based chaos would be nice for regression protection.
      Fix:      Low priority. Consider adding a Testcontainers chaos
                test profile for CI if the team grows.

6. CONFIGURATION & USABILITY GAPS
================================================================================

6.1  No @ConditionalOnClass for Kafka and MongoDB
     ------------------------------------------------
     File: orchestrator-starter/.../autoconfigure/OrchestratorAutoConfiguration.java

     The auto-configuration does not guard on KafkaTemplate or
     MongoTemplate being on the classpath. If either dependency is
     missing, the application fails with an unsatisfied dependency
     error rather than a clear "Kafka/MongoDB required" message.

     Impact:   Low — poor developer experience on misconfiguration.
     Fix:      Add @ConditionalOnClass(KafkaTemplate.class) and
               @ConditionalOnClass(MongoTemplate.class) on the
               auto-configuration class.

6.2  String-Based Step References (Partially Mitigated) [REVISED]
      -------------------------------------------------------------
      File: orchestrator-starter/.../flow/FlowDefinitionScanner.java

      Step names default to method names converted to UPPER_SNAKE_CASE
      via regex: method.getName().replaceAll("([a-z])([A-Z])", "$1_$2").toUpperCase()

      Startup validation IS present and effective:
        - @Compensate(step="...") references are validated against
          discovered @Step method names — throws IllegalStateException
          at startup if invalid.
        - @OnCancel(step="...") references are similarly validated.
        - Duplicate step orders/names are caught at startup.

      Remaining risks (not caught at startup):
        - completedWhen SpEL expressions like "documentId != null" are
          not validated — typos fail silently at runtime.
        - Method renames change the derived step name, which can break
          @Compensate(step=...) references. However, the startup
          validation catches this immediately on next deploy.

      Impact:   Low — @Compensate/@OnCancel references are validated.
                SpEL completedWhen remains unvalidated (Medium).
      Fix:      Add SpEL expression validation at startup (test-evaluate
                against a prototype entity instance). The @Compensate/
                @OnCancel string matching is adequately guarded.

6.3  Per-Flow Retry Config Removed [FIXED]
      -------------------------------------
      File: orchestrator-starter/.../autoconfigure/OrchestratorAutoConfiguration.java
            (orchestratorCommandRetryConfig)

      ORIGINAL: FlowConfig had a retry field that was parsed but never wired
      into RetryTopicConfiguration.

      RESOLVED: The retry field was removed from FlowConfig. The Javadoc
      example still references per-flow retry as an aspirational feature,
      but there is no dead code — no field is parsed and ignored.

      Impact:   FIXED — dead code removed. Javadoc example is aspirational
                documentation for a future feature, not a misleading gap.

6.4  SpEL Expressions in Annotations Are Untyped
     -----------------------------------------------
     File: orchestrator-starter/.../annotation/Step.java (completedWhen)

     completedWhen uses SpEL strings like "documentId != null" that are
     evaluated at runtime against the flow entity. Typos ("documnetId")
     or type mismatches fail silently at runtime (step always re-executes
     or always skips).

     Impact:   Medium — misconfigured completedWhen causes subtle bugs.
     Fix:      Add SpEL expression validation at startup (test-evaluate
               against a prototype entity instance), or support a type-
               safe alternative (e.g., a method reference).

7. PERFORMANCE GAPS
================================================================================

7.1  Full Entity Serialization in Step Logs
     -----------------------------------------
     File: orchestrator-starter/.../flow/FlowOrchestrator.java

     When includeFlowStateInLogs=true, EVERY step execution serializes
     the full entity to JSON twice (before and after). For large
     entities with binary attachments, this is expensive.

     Impact:   Low (disabled by default), high when enabled.
     Fix:      Add a max-size guard — skip serialization if entity
               exceeds a configurable size threshold.

7.2  [REMOVED] Fixed Outbox Poll Interval
      ---------------------------------------
      Original claim: 500ms fixed poll is wasteful when idle, slow under load.
      Removed because: the analysis itself concluded "2 queries/second is
      negligible for MongoDB." Not a real gap — adaptive polling would add
      complexity for no measurable benefit at current scale.

7.3  IndexInitializer Scans All Collections at Startup
     -----------------------------------------------------
     File: orchestrator-starter/.../autoconfigure/IndexInitializer.java
           (getFlowCollections)

     On startup, IndexInitializer iterates ALL MongoDB collections,
     reads one document from each, and checks for status/currentStep
     fields. In a large MongoDB deployment with many collections, this
     is slow and wasteful.

     Impact:   Medium in environments with many collections.
     Fix:      Accept a list of flow collection names in configuration,
               or derive from @Document annotations on scanned entities.

8.1  Auto-Generated REST Endpoints Conflict with Consumer Endpoints

      Removed because: the analysis itself rated this "cosmetic inconsistency."

10. RESILIENCE GAPS
================================================================================

10.1 Compensation Handlers Are Not Transactional
      ---------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java (runCompensation)

      Compensation handlers execute sequentially in the same thread.
      If a compensation handler fails, the remaining handlers are
      still executed, but the flow is marked FAILED regardless. There
      is no compensation log or retry mechanism for failed
      compensations.

      Impact:   Medium — partial compensation leaves system in
                inconsistent state.
      Fix:      Add a COMPENSATION_FAILED status, persist compensation
                progress, and provide a manual retry endpoint.

10.2 No Timeout on Step Execution [FIXED]
      ------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java (executeWithTimeout)

      ORIGINAL: Step handlers executed without a timeout. A misbehaving step
      could block the Kafka consumer thread forever.

      RESOLVED: FlowOrchestrator now has an executeWithTimeout() method that
      wraps handler.execute() in a CompletableFuture with a configurable
      timeout (default 60s, via orchestrator.step.timeout-seconds). Uses
      virtual threads (Executors.newVirtualThreadPerTaskExecutor()). On
      timeout, throws RetryableStepException so the message routes to retry
      topics. Setting timeout to 0 disables the feature.

      Impact:   FIXED — step execution is now bounded by a configurable timeout.

10.3 No Circuit Breaker for Vendor Calls [REMOVED]
       ---------------------------------------
       Original claim: Library should integrate Resilience4j for vendor call
       circuit breaking.
       Removed because: Circuit breakers belong at the HTTP client layer
       (Feign/RestClient configuration), not in the orchestration library.
       The library's contract is retry/fail/recover annotations. Adding
       Resilience4j would couple the library to a specific resilience
       framework. Consumers configure vendor resilience at the client level.

11. NEW GAPS FOUND IN POST-UPDATE RE-SCAN
================================================================================

11.1  Dead-Lettered Outbox Events Accumulate Silently [FIXED]
      -------------------------------------------------------
      File: orchestrator-starter/.../outbox/OutboxPublisher.java

      ORIGINAL: Dead-lettered events accumulated forever with no cleanup.

      RESOLVED: OutboxPublisher now sets publishedAt on dead-lettered events,
      which enables the existing TTL index (configured via
      orchestrator.retention.outbox-days, default 7 days) to clean them up
      automatically. Dead-lettered events are expired on the same schedule
      as successfully published events.

      Impact:   FIXED — TTL-based cleanup now covers dead-lettered events.

11.2  Orphaned Repository Query Method [FIXED]
      -----------------------------------------
      File: orchestrator-starter/.../outbox/OutboxEventRepository.java

      ORIGINAL: Two competing query methods existed, one of which didn't
      filter on deadLettered and could republish dead-lettered events.

      RESOLVED: The orphaned method `findTop100ByPublishedFalseOrderByCreatedAtAsc`
      has been removed. Only the correct method
      `findTop100ByPublishedFalseAndDeadLetteredFalseOrderByCreatedAtAsc`
      remains.

      Impact:   FIXED — no more confusing API surface.

11.3  Step Timeout Uses Virtual Threads Without Thread Interruption [FIXED]
      ------------------------------------------------------------------------
      File: orchestrator-starter/.../flow/FlowOrchestrator.java (executeWithTimeout)

      ORIGINAL: On timeout, the underlying virtual thread continued running,
      leaking resources (connection pool slots, sockets).

      RESOLVED: The TimeoutException catch block now calls future.cancel(true),
      which interrupts the virtual thread. This releases blocking I/O
      resources when the vendor API is hung.

      Impact:   FIXED — thread interruption on timeout prevents resource leaks.

11.4 Step Timeout Default of 60s May Be Too Aggressive for Gate Steps [REMOVED]
      -------------------------------------------------------------------
      Original claim: 60s default may be too short for slow vendor API calls.
      Removed because: The analysis contradicted itself — gate steps exit
      early via WaitingStepException before the timeout fires. 60s is
      reasonable for vendor API calls (createDocument, amendDocument).
      Not a real gap.
